---
name: review-implementation-for-security
description: 実装先プロジェクトのコード差分（比較基準コミットIDからHEADまで）にセキュリティ的な欠陥が無いかをレビューする。「実装にセキュリティ上の問題がないかレビューして」等の依頼、または review-implementation から呼び出されて使用する。
---

引数 `$ARGUMENTS` で渡された「設計書ファイルパス」「比較基準となるコミットID」「実装先プロジェクトのルートディレクトリ」をもとに、以下の手順でレビューしてください。

1. `$ARGUMENTS` から設計書ファイルパス・コミットID・実装先プロジェクトのルートディレクトリを読み取る。設計書パスが相対パスの場合はカレントディレクトリ基準で解釈する
   - いずれか省略されている場合は、独断で進めずユーザーに確認する（大元skillから呼び出された場合は渡された値をそのまま用いる）。コミットIDを自動で提案することはしない
2. 実装先プロジェクトが属するリポジトリのHEAD時点と指定コミットID時点の間のコード変更差分を `git diff` で取得する（未コミットの変更は対象外）
   - コミットIDが不正で解決できない場合はユーザーに確認する
   - 差分が無い場合は、レビュー対象がない旨を返して終了する
3. 設計書が属するリポジトリのHEAD時点の設計書ファイルの内容を、差分の意図を理解する文脈として参照する（未コミットの変更は含めない）
   - HEAD時点で設計書ファイルが存在しない・リネームされている場合や、設計書がGit管理外の場合はユーザーに確認する（大元skillから呼び出された場合はこの確認を省略してよい）
4. コード差分に、以下の観点でセキュリティ的な欠陥が無いか検出する。判断のために差分前後や関連ファイルを参照する場合もHEAD時点の内容を用い、未コミットの変更は文脈にも含めない
   - インジェクション（SQLインジェクション、コマンドインジェクション、XSS等）
   - 認証・認可の不備（認可チェック漏れ、権限昇格の余地等）
   - APIキー・トークン・パスワード等の秘密情報のハードコーディングやログ出力
   - 入力値検証の不足によるリスク（パストラバーサル、不正なファイルアップロード等）
   - 安全でない暗号・ハッシュ関数の使用
   - 差分と無関係な既存コードの脆弱性は対象としない
5. 見つかった指摘事項を、以下の項目を持つリストとして整理する
   - 種別: 「セキュリティ」で固定する
   - 指摘内容
   - 根拠（該当ファイルパス・行）。指摘の記述や根拠に実際の秘密情報の値が含まれる場合は、値をマスクして記載する（例: `AKIA****`）
6. 指摘事項・実行状態（成功）を戻り値として大元skillに返す。この子skill自体はHTMLファイルを作成しない。指摘・根拠にAPIキー・トークン等の秘密情報が含まれる場合は、値をマスクしてから返す・報告する
   - 単独で呼び出された場合は、指摘事項をチャットで報告する
7. 処理中にエラーが発生し完了できない場合は、実行状態を「失敗」とし、失敗理由（秘密情報が含まれる場合はマスクする）とともに大元skillに返す（単独実行の場合はチャットで報告する）
