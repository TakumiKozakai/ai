# todo-app 一覧画面設計書

画面名: Todo一覧画面。対応パス: `GET /todos`（ルートパス `/` から `HomeController` により `/todos` へリダイレクトされた場合も同一画面）。テンプレート: `templates/todo/list.html`。対応コントローラ: `TodoController`（`app/src/main/java/com/example/todo/controller/TodoController.java`）。本書は `03_詳細設計/todo-app全体設計書.md` および実装（`app`）を根拠に作成した一覧画面単体の詳細設計書であり、全体設計書・実装との間に矛盾は確認されなかった。編集画面については「todo-app編集画面設計書.md」を参照。

## 1. 画面項目定義

### 1.1 追加フォーム

| 表示名（論理名） | 種別 | 必須性 | 初期値／表示内容 | 操作可否 | 備考 |
|---|---|---|---|---|---|
| タイトル入力欄 | テキスト入力 | 必須（サーバー側） | 空（プレースホルダ「タイトルを入力」） | 入力可 | `Todo.title` にバインド |
| 詳細入力欄 | テキスト入力 | 任意 | 空（プレースホルダ「詳細(任意)」） | 入力可 | `Todo.description` にバインド |
| 期限入力欄 | 日付入力（`type="date"`） | 任意 | 空 | 入力可 | `Todo.dueDate` にバインド。ブラウザ標準の日付ピッカーUIが提供される |
| 追加ボタン | ボタン（submit） | - | 「追加」 | 押下可 | `POST /todos` を送信 |
| タイトルのエラーメッセージ | テキスト（条件表示） | - | 非表示（タイトルにバリデーションエラーがある場合のみ表示） | 表示のみ | サーバー側バリデーションエラー時に `title` のエラーメッセージ「タイトルは必須です」を表示 |

- 状態（`status`）を指定する項目はこのフォームには表示されない。通常の追加フォーム操作（画面上の入力・送信）では送信データに `status` が含まれないため、追加されるTodoは常に `Todo` エンティティのデフォルト値「未着手」（`NOT_STARTED`）になる。

### 1.2 Todo一覧

一覧行は、Todoが1件以上存在する場合にのみ表示され、各行に以下の項目を持つ。

| 表示名（論理名） | 種別 | 必須性 | 初期値／表示内容 | 操作可否 | 備考 |
|---|---|---|---|---|---|
| 状態セレクトボックス | セレクトボックス | - | 対象Todoの現在の状態（未着手／作業中／完了）が選択済み | 選択可 | 選択変更と同時に自動送信され `POST /todos/{id}/status` が発行される（`onchange="this.form.submit()"`）。選択肢は未着手／作業中／完了の3値のみだが、画面表示は日本語ラベルであり、送信される `status` パラメータの値は `TodoStatus` の定数名（`NOT_STARTED`／`IN_PROGRESS`／`DONE`）である |
| タイトル表示 | テキスト表示 | - | 対象Todoの `title` | 表示のみ | 状態が「完了」の行では取り消し線が表示される（CSS `.todo-item.completed .todo-title`） |
| 詳細表示 | テキスト表示 | - | 対象Todoの `description`（未入力なら空欄） | 表示のみ | - |
| 期限表示 | テキスト表示 | - | 対象Todoの `dueDate`（`LocalDate` の標準文字列表現、例: `2026-09-13`。未設定なら空欄） | 表示のみ | - |
| 編集リンク | リンク | - | 「編集」 | 遷移可 | `GET /todos/{id}/edit` へ遷移 |
| 削除ボタン | ボタン（submit） | - | 「削除」 | 押下可 | `POST /todos/{id}/delete` を送信。クライアント側の確認ダイアログ（`confirm()`等）は実装されておらず、押下と同時に削除リクエストが送信される |

### 1.3 その他

| 表示名（論理名） | 種別 | 必須性 | 初期値／表示内容 | 操作可否 | 備考 |

## 2. 入力チェック内容

### 2.1 クライアント側

- 実装上、追加フォームに `required` などのHTML5必須属性やJavaScriptによる入力チェックは存在しない。タイトル・詳細ともにクライアント側の必須チェックは行われていない。
- 期限入力欄は `type="date"` であるため、対応ブラウザ標準の日付入力UIおよび型制約検証（constraint validation）が働く。`required` 属性は付与されていないため未入力は許容され、`min`/`max` 属性による範囲制約も設定されていない。

### 2.2 サーバー側

| 対象項目 | チェック内容 | エラーメッセージ | 発生条件 |
|---|---|---|---|
| タイトル | 必須（`@NotBlank`）。空文字・空白のみの入力は不可 | 「タイトルは必須です」 | `POST /todos` 送信時 |
| 期限 | `Todo.dueDate`（`LocalDate`）へは `@DateTimeFormat(pattern="yyyy-MM-dd")` により型変換される。Bean Validationによる追加の制約（過去日禁止等）は無いが、`yyyy-MM-dd` 形式に変換できない値が送信されると `BindingResult` にフィールドエラーとして記録され、保存されない | 画面上の表示なし（期限用のエラーメッセージ表示欄はテンプレートに存在しない） | `POST /todos` 送信時。通常の画面操作では `type="date"` のブラウザ標準検証により発生しない |
| 状態（状態変更処理） | `POST /todos/{id}/status` の `status` パラメータを `TodoStatus`（`NOT_STARTED`／`IN_PROGRESS`／`DONE`）へ型変換する。一覧画面のセレクトボックスはこの3値のみを送信するため、通常の画面操作では変換に失敗しない | 表示なし（画面遷移前にエラー応答となるため） | `NOT_STARTED`／`IN_PROGRESS`／`DONE` 以外の文字列を送信するリクエスト改ざん時のみ発生しうる。詳細は3.3を参照 |

- 詳細にはサーバー側のバリデーションは存在しない（任意項目としてそのまま保存される）。
- 状態はこのフォームの送信対象外のため、Todo追加処理でのバリデーション対象にはならない。

## 3. 画面処理

### 3.1 初期表示

- `GET /todos` にアクセスすると、`TodoController#list` が全Todoを取得し、一覧画面を表示する。`todoRepository.findAll()` の呼び出しに明示的なソート指定は無く、取得順序は保証されない。
- モデルには一覧（`todos`）、状態の選択肢（`statuses` = `TodoStatus.values()`）、追加フォーム用の空 `Todo` インスタンス（`newTodo`）が渡される。
- `list()` には `model.containsAttribute("newTodo")` が真の場合に `newTodo` を上書きしない分岐があるが、現在の実装では `GET /todos` の呼び出し時点で `newTodo` が事前にモデルへ設定されているケースは無く、この分岐は実質的に常に空の `Todo` インスタンスを設定する。追加処理のバリデーションエラー時の再表示（3.2）は `list()` を経由せず、`TodoController#create` が直接 `todo/list` を返すことで行われる。

### 3.2 Todo追加（正常時／バリデーションエラー時）

- 追加ボタン押下により `POST /todos` が送信される。
- **正常時**: タイトルが入力されており、かつ期限が空または `yyyy-MM-dd` 形式に型変換可能な値であるなど、`BindingResult` にエラーが記録されない場合、`newTodo` を保存し `/todos` へリダイレクトする。一覧は再取得されるため、追加したTodoが反映された状態で一覧画面が再表示される（フォームの入力値はリダイレクトによりクリアされる）。
- **バリデーションエラー時**: タイトルが空白のみ／未入力の場合、または期限が `yyyy-MM-dd` 形式に型変換できない値の場合、`BindingResult` にエラーが記録され保存は行われない。この場合 `create` はリダイレクトせず、一覧（`todos`）・状態選択肢（`statuses`）を再取得したうえでその場で `todo/list` をそのまま返す。タイトルのエラーであれば、タイトル欄にエラーメッセージ「タイトルは必須です」が表示され、入力済みの詳細・期限の値は保持される。一方、期限のみが型変換エラーとなったケースでは対応するエラーメッセージ表示欄が無いため、画面上にエラー表示が無いまま保存されない結果になる。

### 3.3 状態変更

- 一覧行の状態セレクトボックスを変更すると、変更と同時にそのTodoの状態変更フォームが自動送信され、`POST /todos/{id}/status`（リクエストパラメータ `status`）が発行される。
- 対象Todoが存在する場合のみ状態を更新して保存し、存在しない場合は何も行わない（`findById(id).ifPresent(...)` のため、存在しないID指定時もエラーにはならない）。処理が正常に終了した場合は `/todos` へリダイレクトされ、一覧が再表示される。
- **不正な状態値を送信した場合（通常の画面操作では発生しない）**: `status` パラメータは `@RequestParam TodoStatus status` として受け取られ、`NOT_STARTED`／`IN_PROGRESS`／`DONE` 以外の文字列が渡されると型変換に失敗し `MethodArgumentTypeMismatchException` が送出される。本アプリには当該例外を捕捉する共通例外処理が実装されていないため、Spring Bootのデフォルトエラーページ（Whitelabel Error Page、HTTPステータス400）が表示される。この経路は一覧画面のセレクトボックスからは発生せず、リクエストを直接改ざんした場合にのみ到達する。

### 3.4 編集画面への遷移

- 一覧行の編集リンク押下により `GET /todos/{id}/edit` へ遷移する（画面としては「todo-app編集画面設計書.md」を参照）。
- 対象Todoが存在しない場合は `TodoController#editForm` 内で `IllegalArgumentException`（メッセージ「Todo not found: {id}」）が送出される。本アプリには当該例外を捕捉する `@ControllerAdvice` 等の共通例外処理が実装されていないため、Spring Bootのデフォルトエラーページ（Whitelabel Error Page、HTTPステータス500）が表示される。

### 3.5 削除

- 削除ボタン押下により `POST /todos/{id}/delete` が送信される。
- `TodoController#delete` は `todoRepository.deleteById(id)` を呼び出し、処理が正常に終了した場合は `/todos` へリダイレクトする。
- 対象IDが存在しない場合、本アプリが依存する Spring Data JPA（`spring-data-jpa` 3.3.4、`pom.xml` の Spring Boot 3.3.4 に対応するバージョン）の `SimpleJpaRepository#deleteById` の実装は `findById(id).ifPresent(this::delete)` であり、対象が見つからない場合は例外を送出せず黙って無視する（状態変更処理の `ifPresent` と同じ挙動）。この実装は該当バージョンのクラスファイルを逆コンパイルして確認済みである。したがって、存在しないIDに対する削除要求も例外にはならず、正常時と同様に `/todos` へリダイレクトされる。

### 3.6 例外発生時の共通事項

- 本画面の各処理（Todoの取得・保存・状態更新・削除）でDBアクセス例外等が発生した場合の専用の例外処理・復旧処理は実装されていない。その場合、各処理は通常の成功時の遷移（一覧再表示やリダイレクト）には進まない。
