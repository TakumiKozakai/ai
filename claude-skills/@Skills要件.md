## 使い方

### unit-case-writer（エージェント）

#### 使い方

- メインセッションで、設計書パスを添えて Writer に依頼する。分類は指定しない（常に4分類すべてを作る）
  - 例: `unit-case-writer で 03_詳細設計/todo-app一覧画面設計書.md の試験項目票を作って`
  - 例: `@"unit-case-writer (agent)" 設計書: 03_詳細設計/todo-app一覧画面設計書.md / 出力先: 05_単体試験/claude-playwrite-unit-test`
- 入力: 設計書ファイルパス（必須）、出力先ディレクトリ（省略可。省略時は設計書と同じディレクトリ）、画面名称（省略可）、対象画面機能（イベント。省略可。例:「画面初期表示」「登録ボタン押下」）
  - 対象画面機能を指定すると、4分類ともその機能に絞って作成・レビューする。既存の票があれば該当機能の行だけをマージ（追加・更新。既存行の更新時は上書き可否を確認）し、他機能の既存行は保持する。画面全体の網羅性は保証しない
  - 例: `unit-case-writer で 03_詳細設計/todo-app一覧画面設計書.md の試験項目票を、対象画面機能「登録ボタン押下」に絞って作って`
- 「作成して」以外の指示（分類の限定、ソースの参照等）は受け付けない（無視して最終報告に記載する）
- Writer は判断が必要になると `【要判断】` を返して止まる。メインセッションがその内容をユーザーに確認し、回答を「確認済み回答」（判断できないものは「保留」、やめるなら「中止」）として Writer に `SendMessage` で送ると、止まった位置から再開する

#### 詳細

- 流れ: (1) 設計書から画面名称を特定 → (2) 4分類の `write-unit-case-*` を順に実行して4ファイルを作成（既存ファイルがあれば上書きするか既存を使うかを要判断で確認） → (3) `unit-case-reviewer` を Agent ツールで起動して4ファイルをRv → 分類別の指摘を `write-unit-case-*` の指摘反映モードで反映 → 同じ Reviewer に `SendMessage` で再Rvを依頼、を指摘が無くなるまで最大3回 → (4) 最終報告
- 終了状態: **収束**（4ファイルとも指摘0件）／**見送り残存で終了**（残る指摘がすべて見送り・保留）／**上限打ち切り**（3回目で反映可能な指摘が残る。反映せず報告し、`試験項目票レビュー結果_{画面名称}_完成_{yyyyMMddHHmm}.html` を出力）／**要確認事項待ちで中断**／**ユーザー中止**
- 「他分類への移動が必要な行」は Writer が移動先の票へ「抜け（新規）」で追加させ、移動元の票へ「削除」を指示して自分で動かす
- Writer・Reviewer ともローカルファイルの静的解析だけで動く（実行中アプリ・DB・MCP・外部サービスに接続しない）。レビューは設計書ベースのみ
- 収束しても自動反映のみで完結させず、最終的な人による目視レビューを推奨する旨を毎回報告する
- メイン → Writer → Reviewer の2階層の入れ子を使う。`CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH` を 1 にしていると動かない

### unit-case-reviewer（エージェント）

#### 使い方

- 通常は unit-case-writer から呼ばれるため、ユーザーが意識する必要は無い
- 既存の試験票を単体でRvしたいときは直接呼ぶ
  - 例: `unit-case-reviewer で 05_単体試験/claude-playwrite-unit-test/試験項目票_Todo一覧画面_01_正常系.md を 03_詳細設計/todo-app一覧画面設計書.md でレビューして`
- 入力: 設計書ファイルパス（必須）、試験項目票ディレクトリ（省略可）、画面名称（省略可）、レビュー対象の分類またはファイル名（省略時はディレクトリにある担当ファイルすべて）、確認済み回答

#### 詳細

- 分類ごとに対応する `review-unit-case-*` を Skill ツールで実行し、分類別に指摘一覧（種別・対象No.・シナリオ・指摘内容・根拠）・実行状態・要確認事項を返す
- Writer から「集約実行」と明示されたときはHTMLを作らない。ユーザーから直接呼ばれた単体実行では、指摘が1件以上あれば `試験項目票レビュー結果_{画面名称}_{分類}_設計書_{yyyyMMddHHmm}.html` を作る（0件ならチャット報告のみ）
- `SendMessage` で再Rvを依頼されたときは、記憶ではなくファイルを再読して現状をRvし、前回指摘の解消も確認する
- 試験票・設計書は変更しない。`Edit` / `NotebookEdit` / `Agent` は禁止

### write-unit-case-normal-case

#### 使い方

- unit-case-writer が Skill ツールで実行する手順書（`user-invocable: false`）。ユーザーは直接呼ばない
- `$ARGUMENTS` は「通常モード」と「指摘反映モード」で内容が異なる
  - 通常モード: 設計書ファイルパス（必須）、出力先ディレクトリ（省略可）、画面名称（省略可）、上書き可（既存ファイルを上書きするとき）、確認済み回答（あれば）。対象画面機能（イベント。Writer から渡される。指定時は該当機能の行だけを起票し、既存ファイルにはマージする）
  - 指摘反映モード: 設計書ファイルパス、出力先ディレクトリ、画面名称、指摘一覧（種別・対象No.・シナリオ・指摘内容・根拠）、確認済み回答（あれば）。指摘一覧が含まれていれば指摘反映モードとして動作する

#### 詳細

- 通常モード: 設計書のフロント処理・サーバ処理の正常な操作フロー、一覧表示、正常に受理される境界値（文字数上限ちょうど等）を洗い出し、No./シナリオ/正常異常/前提条件/操作手順/期待結果の表として `試験項目票_{画面名称}_01_正常系.md` に保存する。画面要素は物理名でなく論理名で記述し、No.は実行可能な順（非永続の表示確認→登録→境界値→削除・0件確認の順）に並べる
- 指摘反映モード: 既存の票を読み込み、指摘を種別ごとに反映する（抜け＝行追加、誤り＝行修正、分類誤り＝列値訂正のみ、表記ゆれ＝修正、削除＝Writer が他分類へ移動した行を消す）。対象行は対象No.とシナリオの両方一致で特定し、一致しない・複数該当する場合は反映せず要確認事項として返す
- 「他分類に属する項目が含まれている」という分類誤りの指摘は、行を削除せず「他分類への移動が必要な行」として移動先分類と行の全内容を報告する（移動は Writer が行う）
- サブエージェント内で動くため質問できず、判断に迷う事項は起票・反映せず「要確認事項」として返す。既存ファイルがあり上書き可の明示が無い場合も同様
- 画面名称は引数で渡されていればそれを用い、無く設計書から一意に特定できない場合は保存せず状態「失敗」で候補を返す

### write-unit-case-server-error

#### 使い方

- `write-unit-case-normal-case` と同じ引数構成（通常モード／指摘反映モード。対象画面機能による絞り込み・マージも同じ）
- 担当ファイルは `試験項目票_{画面名称}_02_異常系.md`

#### 詳細

- 仕組みは `write-unit-case-normal-case` と同一。対象はDB接続断・制約違反、ファイル操作エラー、AWSサービスアクセスエラー等、外部リソース起因の異常
- 前提条件に外部リソースを異常状態にする手順、操作手順の末尾に正常状態へ復旧させる手順を必ず含める
- No.の並びでは、外部リソースを異常にする項目を最後にまとめて配置し、各項目内で復旧まで完結させて他の項目に影響を残さない。指摘反映モードで行の並び替えが起きた場合もこのルールを維持する

### write-unit-case-front-validation

#### 使い方

- `write-unit-case-normal-case` と同じ引数構成（通常モード／指摘反映モード。対象画面機能による絞り込み・マージも同じ）
- 担当ファイルは `試験項目票_{画面名称}_03_フロントバリデーション.md`

#### 詳細

- 仕組みは `write-unit-case-normal-case` と同一。対象は「フロント側でエラーとして拒否される境界値」（文字数上限超過・必須未入力等）と相関項目チェック
- 正常/異常列は常に「異常」を記載し、期待結果に表示されるエラーメッセージ文言を具体的に書く
- サーバ側にも同じ検証がある場合、フロント視点の項目として重複起票してよい（サーババリデーション票との重複は分類誤りとしない）
- DB検証は通常不要（フロントで弾かれサーバに到達しない想定）だが、必要な場合は記載できる

### write-unit-case-server-validation

#### 使い方

- `write-unit-case-normal-case` と同じ引数構成（通常モード／指摘反映モード。対象画面機能による絞り込み・マージも同じ）
- 担当ファイルは `試験項目票_{画面名称}_04_サーババリデーション.md`

#### 詳細

- 仕組みは `write-unit-case-normal-case` と同一。対象は「サーバ側でエラーとして拒否される境界値」と相関項目チェック
- フロントのチェックを回避してサーバへ直接不正な値を送るケース（開発者ツールでの属性無効化、curl直叩き等）を操作手順に具体的に記述し、期待結果にHTTPステータス・エラーメッセージを書く
- フロント側にも同じ検証がある場合、サーバ視点の項目として重複起票してよい（フロントバリデーション票との重複は分類誤りとしない）

### review-unit-case-normal-case

#### 使い方

- unit-case-reviewer が Skill ツールで実行する手順書（`user-invocable: false`）。ユーザーは直接呼ばない（単体Rvは unit-case-reviewer を呼ぶ）
- 引数: 設計書ファイルパス（必須）、試験項目票ディレクトリ（省略可。省略時は設計書と同じディレクトリ）、画面名称（省略可）、確認済み回答（あれば）、集約実行（Writer 経由の場合）。対象画面機能（イベント。Writer 経由で渡される。指定時はその機能に関する行・観点だけをRvする）

#### 詳細

- `試験項目票_{画面名称}_01_正常系.md` を設計書と突き合わせ、抜け（対応する行が無い正常フロー・境界値・DB確認用クエリ）、誤り（遷移先・表示文言の不一致、物理名の使用、No.の連番違反・並び順違反、DB定義との不整合等）、分類誤り（正常/異常列や他分類項目の混入）、表記ゆれを検出する
- 指摘は重大度順（抜け＞誤り＞分類誤り＞表記ゆれ）に整理し、種別・対象No.（新規は「(新規)」）・指摘内容・根拠を持つ
- 集約実行の場合はHTMLを作らず、指摘一覧・実行状態・要確認事項を呼び出し元に返す。単体実行の場合は指摘が1件以上あれば `試験項目票レビュー結果_{画面名称}_01_正常系_設計書_{yyyyMMddHHmm}.html` を作成する
- サブエージェント内で動くため質問できず、判断に迷う観点は「要確認事項」として返す。渡された確認済み回答は再確認せず用い、設計書の記載と矛盾する場合は確認済み回答を優先する
- 根拠はローカルファイルの静的解析のみ。実行中アプリ・DB（MCP含む）・外部サービスには接続しない。DB定義との照合は設計書のDB定義記述だけを根拠にし、無ければ要確認事項として返す
- 試験項目票・設計書は変更しない（レビューのみ）

### review-unit-case-server-error

#### 使い方

- `review-unit-case-normal-case` と同じ引数構成（対象画面機能による絞り込みも同じ）
- 担当ファイルは `試験項目票_{画面名称}_02_異常系.md`

#### 詳細

- 仕組みは `review-unit-case-normal-case` と同一。観点は設計書上の外部リソースアクセス処理ごとにエラー系の行があるか、前提条件に異常状態の具体的記述があるか、操作手順末尾に復旧手順があるか、異常項目が最後にまとめて配置され前後に影響しない並びになっているか
- 秘密情報（接続文字列・認証情報等）が指摘・根拠に含まれる場合はマスクする
- 単体実行時のHTML名は `試験項目票レビュー結果_{画面名称}_02_異常系_設計書_{yyyyMMddHHmm}.html`

### review-unit-case-front-validation

#### 使い方

- `review-unit-case-normal-case` と同じ引数構成（対象画面機能による絞り込みも同じ）
- 担当ファイルは `試験項目票_{画面名称}_03_フロントバリデーション.md`

#### 詳細

- 仕組みは `review-unit-case-normal-case` と同一。観点はフロント側の入力チェック仕様（必須・文字数・形式・相関項目チェック）に対応する行の有無、エラーメッセージ文言の一致、DB検証記述の要否（フロントで弾かれる想定のため通常不要という前提自体も検証する）
- 正常に受理される境界値・サーバ側バリデーション・サーバエラーが混入していれば分類誤りとするが、フロント・サーバ双方で同じ検証を起票した重複は分類誤りとしない
- 単体実行時のHTML名は `試験項目票レビュー結果_{画面名称}_03_フロントバリデーション_設計書_{yyyyMMddHHmm}.html`

### review-unit-case-server-validation

#### 使い方

- `review-unit-case-normal-case` と同じ引数構成（対象画面機能による絞り込みも同じ）
- 担当ファイルは `試験項目票_{画面名称}_04_サーババリデーション.md`

#### 詳細

- 仕組みは `review-unit-case-normal-case` と同一。観点はサーバ側の入力チェック仕様に対応する行の有無、フロント回避手順（開発者ツール・curl等）の具体性、レスポンスのHTTPステータス・エラーメッセージの一致
- フロント・サーバ双方で同じ検証を起票した重複は分類誤りとしない。画面のサーバ処理検証のための直接リクエストはAPI用試験項目票の対象として除外しない
- 単体実行時のHTML名は `試験項目票レビュー結果_{画面名称}_04_サーババリデーション_設計書_{yyyyMMddHHmm}.html`

### Skill名

#### 使い方

#### Skillの詳細
