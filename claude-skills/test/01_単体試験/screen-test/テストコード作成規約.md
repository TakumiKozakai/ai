# 試験項目からテストコードを作る際の規約

この文書は `write-playwright-unit-test` と `run-playwright-unit-test` の共通契約。
試験票が期待結果の正本、specと設定が実行内容、対応表が両者の対応を記録する。

## 1. ファイル構成とパス

```text
screen-test/
  specs/
    evidence.js
    <suite-id>.spec.js
  plans/<suite-id>/
    mapping.md
    config.example.json
    config.local.json       実施時に用意する。Git管理外
  runs/<run-id>/            実施結果。Git管理外
```

- suite-idは `todo-required` のような英小文字・数字・ハイフン。画面・分類ごとに重複させない。
- `specs/` に配置するspecからのfixture参照は `./evidence.js`。
- 設定の `cases[].spec` は `specs/` 基準。設定ファイルをplans配下に置いても変わらない。
- コマンドは `screen-test/` で実行する。スキルを呼ぶセッションは親の `01_単体試験/` で起動する。
- 対応表の元票パスは `screen-test/` 基準。元票・No.・シナリオで同一性を確認し、No.だけで別票の試験を流用しない。

## 2. 変換ルール

| 試験票 | テストコード・設定 |
| --- | --- |
| No. 1 | case.id = `No1`、test名 = `No1 シナリオ` |
| 操作手順 | `step('手順1 …', async () => {...})`。打鍵ごとに分割 |
| 画面の期待結果 | locatorに対する `expect`。表示だけでなく指定された文言・値・件数も照合 |
| DB確認SQL | `cases[].database.query`。実行前後に同じSELECTを実施 |
| DBが変わらない | `unchanged: true`（票に根拠がある場合のみ） |
| DBが指定状態になる | `expectedAfter`。必要なら `expectedBefore` も指定 |
| S3オブジェクトが存在する | `s3.expectedKeys` に完全なキーを列挙 |
| EC2ログに指定文言が存在する | `ec2.contains` に全期待文字列を列挙 |
| S3・EC2が対象外 | 各サービスに `notApplicable` と根拠となる理由 |

論理名は `getByRole`・`getByLabel`・`getByPlaceholder` 等で特定する。重複するボタンは対象行などで絞り込む。
DOMにラベル等がなく物理locatorが必要なら、確認したソースの箇所と理由を対応表に記録する。
ソースを確認できないlocatorを断定せず、未検証であることを残す。
固定sleepで完了を推測せず、票の期待に合う表示・レスポンス・状態を待つ。

## 3. spec例

以下は形式の例。実際には票の操作・文言に置き換える。

```javascript
import { test, expect } from './evidence.js';

test('No1 タイトル未入力時は登録されない', async ({ page, step }) => {
  await step('手順1 一覧を開く', async () => {
    await page.goto('/todos');
    await expect(page.getByRole('heading', { name: 'Todoアプリ', exact: true })).toBeVisible();
  });
  await step('手順2 タイトルを空欄にする', async () => {
    await page.getByPlaceholder('タイトルを入力', { exact: true }).fill('');
  });
  await step('手順3 追加を押しエラーを確認する', async () => {
    await page.getByRole('button', { name: '追加', exact: true }).click();
    await expect(page.getByText('タイトルは必須です', { exact: true })).toBeVisible();
  });
});
```

`step` が撮影・HTMLへの添付を行う。独自に同名画像を上書きしたり、失敗をcatchして成功扱いしたりしない。
`test.only`、`test.skip`、`test.fixme`、期待された失敗を合格扱いする `test.fail` は生成しない。
試験ファイルのトップレベル・設定読込時は外部コマンドや通信を実行しない。
試験コード内から別途DB/AWSの確認を呼ばず、runnerの証跡・判定と二重管理しない。

## 4. 設定の契約

接続設定の形式は [config.example.json](config.example.json)、AWS対象外の場合は
[config.todo-local.json](config.todo-local.json) を参照する。

| 項目 | 型・内容 |
| --- | --- |
| `baseUrl` | 認証情報を含まないHTTP(S) URL |
| `allowedOrigins` | 起点URLとして許可するorigin配列。対象URLから黙って許可リストを広げない |
| `database` | `host`、`port`（省略時5432）、`name`、読み取り用`user` |
| `aws` | AWSを使う場合の `profile`、`region`、12桁の `accountId` |
| `cases` | 票の実施順の配列。実装済みの対象No.と1対1 |
| `cases[].database.query` | 単一SELECT。末尾セミコロン・psqlメタコマンドなし |
| `expectedBefore` / `expectedAfter` | JSONの行オブジェクト配列。未指定と空配列 `[]` は異なる |
| `s3` | `bucket`、`prefix`、空でない `expectedKeys` 配列、または理由付き `notApplicable` |
| `ec2` | `instanceId`、絶対パスの `logPath`、`lines`（1〜1000）、空でない `contains` 配列、または理由付き `notApplicable` |

DBは列名・JSON型・行順まで比較する。票のSQLの意味を維持し、順序を固定する必要があれば
根拠を確認して `ORDER BY` を追加する。末尾セミコロンの除去のような機械的正規化も対応表に記録する。
現在の実装では1ケースに1クエリ。複数テーブルが必要で単一クエリにまとめられない場合は機能不足として相談する。
自動採番ID・生成日時を固定値で比較したいが値が決まらない場合、票の確認意図を保つ投影・集約SQLを相談する。
単純な固定値に置き換えて検証を弱めない。

設定例には秘密値を入れない。実接続値は実施者が `config.local.json` に設定し、DBパスワードは
`.pgpass` / `PGPASSFILE`、AWSはプロファイルに設定する。認証済みブラウザ状態が必要なら
Git管理外の `.runtime/auth/` 等に置き、準備方法と必要な環境変数を対応表に記載する。
認証方式が未指定なら勝手にログイン手順・認証回避を生成しない。

## 5. 実行方式による制約

- runnerはcases順に1件ずつ別のPlaywrightプロセスで実行する。各No.のブラウザ・変数・`beforeAll` は共有されない。
- 前No.が作った永続データを使う場合、その依存を対応表に記録し、当該No.でも前提をassertionや `expectedBefore` で確認する。
- runnerはあるNo.が失敗しても後続No.を試みる。前No.成功だけに依存したまま後続を合格させない。
- DBの事前取得はspec起動前。spec内部でデータ準備すると、その変更も前後差分に入る。
  初期データは実施前に用意するか、票が認める準備操作とその差分を明示する。
- 画面変更は試験票に指定された操作のみ。無断のDB復元・S3削除・自動リセットは生成しない。
- 同じコードでも初期データが違えば結果は変わる。更新系試験は再実行前の準備を必ず定義する。
- 1件のtest名が他のtest名の末尾と一致するとrunnerのgrepが複数件を選ぶ場合がある。
  一意の `NoN シナリオ` とし、実施前にrunnerと同じファイル・タイトル条件で1件だけ列挙されることを確認する。

## 6. 現在対応していない期待結果

| 要求 | 扱い |
| --- | --- |
| DB確認不要のケース | runnerはDB必須。確認方法の合意またはrunner拡張が必要 |
| S3の不在・内容・ハッシュ・今回生成されたことの確認 | 現在は期待キーの存在のみ。コード生成時に機能不足として提示 |
| EC2ログの期間指定・不在・厳密な件数・圧縮ログ | 現在は固定ファイル末尾の文字列包含のみ。別方式が必要 |
| SSH / CloudWatch Logs経由のログ確認 | 現在はLinux EC2へのSSM。別方式が指定されたら実装変更を相談 |
| DB断・AWS障害など外部リソースへの障害注入 | `_02_異常系` は対象外。自動で障害を起こさない |

不足する機能を、無関係な確認や `notApplicable` への変更で代替しない。
S3キーやログ文言が既存データにも一致する場合は、試験固有のキー・相関IDなどの決め方を確認する。
未確定事項が解消するまで「実施準備完了」としない。

## 7. 更新・受け渡し

元票SHA-256は生バイト列から取得する。改行等の変更でもハッシュが変わるため、実施者は差分を確認する。
ハッシュは変更検出用であり、内容が正しく実装されたことを保証しない。実施前には対応表とコードも読む。
作成者はspec・設定例・対応表をセットで渡す。実施者は接続情報だけをローカル設定に補完し、
No.・順序・locator・SQL・期待値の変更が必要なら作成スキルに戻す。
