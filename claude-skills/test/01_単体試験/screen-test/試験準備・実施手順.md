# スキルによる試験準備・実施手順

この手順は、レビュー済み試験項目票からコードを作り、準備後に試験を実施するためのもの。
クライアント導入と疎通確認は現時点では保留している。以下に将来実施する手順を記載するが、自動実行はしない。

## 1. 使用するスキル

| 作業 | スキル | 成果物 |
| --- | --- | --- |
| 試験項目からコード作成・更新 | `write-playwright-unit-test` | spec、確認設定例、No.対応表・未確定事項 |
| 準備確認・試験実施・結果報告 | `run-playwright-unit-test` | HTML結果票、画面・DB・AWSの証跡 |

既存構成に合わせ、どちらも `test/01_単体試験/.claude/skills/` に配置している。
Claude Codeを次のディレクトリで起動する。CLI実施にMCPサーバーの登録は不要。

```bash
cd claude-skills/test/01_単体試験
claude
```

このリポジトリ内のClaude Code用スキルとして使用する。Codexのグローバルスキルへのインストールは行っていない。

## 2. コード作成前に揃える情報

| 情報 | 必要な内容 | 不足している場合 |
| --- | --- | --- |
| 試験項目票 | Markdown1ファイル、No.、前提、操作、期待結果、必要なDB確認SQL | 対象No.を特定して確認 |
| 画面実装 | ソースまたは確認済みDOM・locator情報 | 確定できないlocatorを保留 |
| 対象環境 | 画面URL・起点origin | 設定例に未確定として残す |
| DB | ホスト・ポート・DB名・読み取りユーザー、SQLと前後期待 | DB確認を勝手に省略しない |
| S3 | 要否、bucket・prefix・期待キー | 未指定と対象外を区別 |
| EC2 | 要否、SSM接続先・ログパス・行数・期待文言 | 同上 |
| 認証 | ログイン方式・認証状態の準備方法 | 推測して実装しない |
| データ | 初期状態・試験間依存・再実行時の準備 | 更新系試験の開始前に解決 |

パスワード・AWSアクセスキーはチャットや試験票に記載しない。
接続先が未確定でも、確定済みの操作のコード作成と未確定事項の整理はできる。

## 3. コード作成を依頼する

Claude Codeへの依頼例（パスはセッションのcwd基準）:

```text
write-playwright-unit-test で次の試験項目票からコードを作ってください。
試験項目票: 01_試験項目/試験項目票_Todo一覧画面_04_サーババリデーション.md
アプリソース: ../../app
設計書: ../../doc/詳細設計/todo-app一覧画面設計書.md
suite-id: todo-server-validation
S3・EC2: このローカルTodo試験では対象外
実際の試験・接続・クライアント導入はしないでください。
```

既存票が `試験項目票/` など別フォルダにある場合は実在するパスを指定する。
このリポジトリの動作例として、`screen-test/試験項目票_Todo一覧画面_04_サーババリデーション.md` も利用できる。
既存サンプルの受け渡し例は [plans/todo/mapping.md](plans/todo/mapping.md) と [設定例](plans/todo/config.example.json)。環境準備は保留中で、実施済みを意味しない。
ファイルを探しても候補が複数なら、スキルが使用する票を確認する。

作成されるファイル:

```text
screen-test/specs/todo-server-validation.spec.js
screen-test/plans/todo-server-validation/config.example.json
screen-test/plans/todo-server-validation/mapping.md
```

作成スキルは構文・テスト列挙・設定検証まで実施できる。アプリやDB・AWSへ接続しない。
未導入ツールがあれば静的検証を「未検証」として残し、勝手にインストールしない。

## 4. 受け取ったコードを確認する

`mapping.md` で以下を確認する。

- 元票のパス・No.と、生成された全test・casesが1対1で一致する
- 操作・画面assertion・DB前後・S3・EC2が票の期待を満たす
- 保留事項が解決済みで、対象外に根拠がある
- 初期データ・認証・ケース間依存・再実行手順が定義されている
- ローカル設定の接続値以外を変更していない

修正する場合は同じ作成スキルに「票の変更内容と対象No.」を渡す。
試験を通すために期待結果を実際の結果に合わせない。票の修正が必要な場合は先に票をレビューする。

## 5. 実施する時点で環境を準備する

導入・認証の詳細は [構築手順書](構築手順書.md)。実施者が対象環境で以下を準備する。

1. Node・Python・Playwright・Chromium・psql、AWSを使う場合はAWS CLIを導入する。
2. 試験用アプリ・DBと初期データ、必要な認証状態を準備する。
3. DB読み取り権限、S3一覧権限、SSMの対象EC2・ログ読み取りが可能な構成を準備する。
4. `config.example.json` を同じフォルダの `config.local.json` にコピーし、接続値を設定する。
5. `.pgpass` / `PGPASSFILE` とAWSプロファイルを準備する。SSMはEC2上でコマンドを実行するため、対象と権限を確認する。
6. ローカル設定・実施範囲・画面から行う更新／削除操作の承認を確認する。

コピー例（`screen-test/` で実行。既存のローカル設定がある場合は上書きしない）:

```bash
cp -n plans/todo-server-validation/config.example.json plans/todo-server-validation/config.local.json
```

準備が揃ったかの静的確認:

```bash
python3 runner.py --config plans/todo-server-validation/config.local.json --validate
bash with-runtime.sh node node_modules/@playwright/test/cli.js test 'specs/todo-server-validation\.spec\.js$' --list --reporter=json
```

上記は接続テストではない。疎通確認を依頼する場合は対象接続先と範囲を指定する。
試験実施スキルは疎通不足を理由に別環境へ接続したり、DB・S3を初期化したりしない。

## 6. 試験実施を依頼する

```text
run-playwright-unit-test で次の試験を実施してください。
試験項目票: 01_試験項目/試験項目票_Todo一覧画面_04_サーババリデーション.md
対応表: screen-test/plans/todo-server-validation/mapping.md
実行設定: screen-test/plans/todo-server-validation/config.local.json
対象: 票の全No.
初期状態・認証・実行対象の確認: 準備済み（実際の確認内容を記載）
```

未確定事項・票の変更・設定の不一致がある場合、実施スキルは実行前に報告する。
試験実施中にコードを生成し直したり、無断で失敗した試験を再実行したりしない。

手動実施する場合も同じ設定を使用する（`screen-test/` で実行）:

```bash
bash with-runtime.sh python3 runner.py --config plans/todo-server-validation/config.local.json
```

`npm test` は従来のルート `config.local.json` 用。票ごとのplansを使う場合は上記の `--config` 指定を使用する。

## 7. 結果確認・再実行

実行時に表示される `runs/<run-id>/index.html` を開く。各No.の画面・DB・S3・EC2を確認する。

| 結果 | 意味 |
| --- | --- |
| PASS | その確認を実施し期待を満たした |
| FAIL | assertion不一致・接続失敗・証跡取得失敗など |
| NOT_RUN | 前提が満たされず未実施。合格ではない |
| NOT_APPLICABLE | 理由を明記した対象外。そのサービスの確認成功ではない |

summaryのchecks件数は試験No.件数ではない。No.別に画面・DB・AWSを集約し、対象件数・合格・不合格・未実施を報告する。
通常の試験失敗でも事後DB・AWSの取得を試みる。起動失敗・強制終了等で結果ファイルがない場合も未実施または実施失敗として記録する。

再実行前は原因、コード／期待値の修正要否、初期データの状態を確認する。
修正が必要なら作成スキルへ戻し、元票・対応表との整合性を確認する。
再実行時も証跡を別run-idに保存し、以前の結果は削除しない。
