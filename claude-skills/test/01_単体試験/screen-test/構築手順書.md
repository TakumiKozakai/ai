# 画面・DB・ログ・S3・EC2確認ツール 構築手順書

試験票からのコード作成・準備確認・試験実施は [スキルによる試験準備・実施手順](試験準備・実施手順.md) を参照する。
以下の導入・接続コマンドは準備する際の手順であり、記載だけで実行の許可を意味しない。

## 1. 構成

画面操作は Playwright Test の CLI (`playwright test`) で固定した TypeScript の試験を実行する。
runner・fixture・単体テストもすべて TypeScript で、Node.js が型注釈を除去して直接実行する（ビルド工程なし）。
対話操作用の `@playwright/cli` とは異なる。試験実行中はLLM・MCPを使用しない。

| 対象 | 実行方法 | 証跡・判定 |
| --- | --- | --- |
| 画面 | Playwright Test / Chromium | 操作ごとのPNG、assertion、失敗時trace、HTML |
| 事前データ | `psql`、SQLファイルを単一トランザクションで実行 | 試験No.ごとの実行ファイル・SHA-256（`seed.json`） |
| PostgreSQL | `psql`、読み取り専用トランザクション | 試験No.ごとの名前付き複数SELECTの前後JSON、期待値または前後一致 |
| アプリログ（ローカル） | ログファイルのバイト位置 | 打鍵中に追記された部分（`app.log`）、期待文字列の存在 |
| S3 | AWS CLI `s3api list-objects-v2` | prefix配下の一覧JSON、期待するキーの存在 |
| EC2内ログ | AWS CLI / SSM Run Command | 指定ファイルの末尾、期待文字列の存在 |
| 集約 | `src/runner.ts`（Node.js 標準ライブラリのみ） | `runs/<UTC日時>-<ID>/index.html` と `summary.json` |

各No.について事前データ投入→DB事前確認→ログ位置記録→画面操作→DB事後確認→アプリログ→S3→EC2の順に実施する。
画面が失敗しても事後の証跡取得は継続し、S3が失敗してもEC2確認は実施する。
事前データ投入・DB事前確認・AWSアカウント照合のいずれかに失敗した場合、画面操作は実施しない。
強制終了・OS停止・ディスク障害では証跡の保存を保証しない。

## 2. 前提ツール

- Node.js 22.18以上とnpm（`.ts` の直接実行＝型ストリップが標準で有効な版。実際に起動できること）
- PostgreSQLクライアント `psql`（既存DBはPostgreSQL 17。ローカルもAWS側DBも同じ `psql` で接続する）
- AWS CLI v2（S3・EC2を実施する場合）
- 稼働中の試験対象アプリ・DB。ECサイトは `../../../app/`（React + Go、PostgreSQL は Docker）で起動する。

作業ディレクトリは以下。以降のコマンドはこのディレクトリで実行する。

```bash
cd claude-skills/test/01_単体試験/screen-test
node --version
npm --version
psql --version
aws --version
```

今回確認した端末はmacOS 12.7.6 / Intel。`/usr/local/bin/node` はNode 16を指し、ICUライブラリ不足で起動しなかった。
そのためNode.js 22.23.2を `.runtime/node-v22.23.2-darwin-x64/` に導入した。
`bash with-runtime.sh <コマンド>` はこのNodeを優先し、ブラウザ・npmキャッシュもツール配下に保存する。
既存のシステムNodeは変更していない。他の端末では利用可能なNode.js 22.18以上をPATHに準備する。

この端末のmacOS 12はPlaywrightが文書で示す対応OSの範囲外。
Playwright 1.55.1 / Chromium 140に固定してローカル動作を確認するが、
正式な運用環境は[公式の対応OS](https://playwright.dev/docs/intro#system-requirements)を満たすこと。
最新Playwrightへの更新は対応OSで実施する。OS自体のアップグレードはこの構築には含めない。

tar -xzf .runtime/downloads/node-v22.23.2-darwin-x64.tar.gz -C .runtime

## 3. Playwright導入

以下はネットワークからnpmパッケージとChromiumを取得する。

```bash
bash with-runtime.sh npm ci --ignore-scripts --no-audit --no-fund
bash with-runtime.sh npm run install:browser
bash with-runtime.sh npm run test:list
```

Playwright 1.55.1を `package.json` と `package-lock.json` に固定している。
`npm ci` は依存ディレクトリを再構築するため、既存 `node_modules/` を保持したい場合は実行しない。
バージョン更新時はブラウザも更新して試験する。
`test:list` ではサンプルの `No1 キーワードで試験用商品を検索できる`（ECサイト）と `No1 タイトル未入力時は登録されない`（旧Todo）が列挙されること。

TypeScript の型チェック・単体テスト（DB・AWS・ブラウザに接続しない）:

```bash
bash with-runtime.sh npm run typecheck
bash with-runtime.sh npm run test:unit
```

`.ts` は Node.js の型ストリップで実行するため、`enum`・`namespace`・コンストラクタ引数プロパティなど型除去だけで消せない構文は使えない（`tsconfig.json` の `erasableSyntaxOnly` で検出する）。import には `.ts` 拡張子を付ける。

DB・AWS・アプリに接続しない動作確認:

```bash
bash with-runtime.sh npm run test:smoke
```

2件の試験で実ブラウザの入力・クリック・PNG保存と、操作失敗時のPNG保存を確認する。
これはメモリ上の検証用HTMLに対する試験であり、アプリの試験ではない。
既定の保存先は `test-results/`。`EVIDENCE_DIR` に別の絶対パスを指定して証跡を分けられる。
エージェントのサンドボックス内でChromiumがSIGTRAP終了する場合は、許可された通常の端末で実行する。

## 4. DB接続

### 4.1 psql の導入（Mac 本体）

ローカル（Docker の PostgreSQL）と開発環境（AWS 側 DB）で同じ `psql` を使い、接続先は設定 JSON だけで切り替える。
Homebrew の `libpq` はクライアントのみで、PostgreSQL サーバーは入らない。keg-only のため PATH に追加する。

```bash
brew install libpq
echo 'export PATH="$(brew --prefix libpq)/bin:$PATH"' >> ~/.zshrc   # bash の場合は ~/.bash_profile
exec $SHELL -l
psql --version
```

### 4.2 試験専用ユーザー `playwright_user`

事前データ投入と DB スナップショットは、試験専用ユーザー `playwright_user` の1つで行う。
全テーブルの SELECT/INSERT/UPDATE/DELETE と全シーケンスの利用権限を持ち、テーブル作成・変更などの DDL 権限は持たない。
スナップショットは権限に関係なく読み取り専用トランザクション（`default_transaction_read_only=on`）で取得する。

ローカルでは `../../../app/docker/.env` に `POSTGRES_PLAYWRIGHT_PASSWORD` を設定したうえで、次のどちらかで作成する。

- DB を作り直す場合: `04_create_playwright_user.sh` が初回起動時に自動実行される（`../../../app/docker/DB再作成手順.md`）
- 既存ボリュームに追加する場合: `../../../app/docker/setup-playwright-user.sh`（繰り返し実行してよい）

AWS 側 DB では、DB 管理者が同じ権限のユーザーを作成する。
既存DBの権限変更を伴うため、実行はDB管理者の承認範囲で行う。

### 4.3 パスワード

パスワードは設定JSON・コマンド引数・Gitに記載しない。`~/.pgpass` または `PGPASSFILE` に指定するファイルへ以下の形式で保存する。
DB名は `app/docker/.env` の `POSTGRES_DB` と同じ値にする。

```text
localhost:5432:<DB名>:playwright_user:<パスワード>
```

```bash
chmod 600 ~/.pgpass
```

外部DBでTLSが必要な場合は `PGSSLMODE=verify-full` と `PGSSLROOTCERT` を設定する。
接続先のhost・port・name・userはJSONで指定し、パスワード入力待ちは無効。

### 4.4 事前データ（seed）

試験項目票の前提条件に必要なデータは、`plans/<suite-id>/seed/*.sql` に書き、設定の `cases[].seed` に指定する。

- runner は接続先の DB 名・ユーザーが設定と一致することを確認してから、指定ファイルを `psql -1`（全ファイルで1トランザクション）で実行する。1文でも失敗すれば全体が取り消され、画面操作は実施しない。
- 設定トップの `database.allowSeed: true` が無い設定では seed を拒否する。共有環境・本番相当の DB を指す設定では `allowSeed` を付けない。
- seed ファイルは `plans/` 配下の `.sql` に限る。psql メタコマンド（`\` を含む行）と `BEGIN;`・`COMMIT`・`ROLLBACK` などのトランザクション制御は書けない。
- 試験用データは `PW_` などの接頭辞で識別し、「前回分を削除→登録」の形で書いて何度実行しても同じ状態にする。初期データや他の試験のデータ、テーブル全体の削除（`TRUNCATE`・条件なし `DELETE`）は行わない。
- 実行したファイルとその SHA-256 は `seed.json` に残る。

### 4.5 スナップショット用クエリ

`cases[].database.queries` に `{名前: SELECT}` で複数指定でき、1つの読み取り専用トランザクションでまとめて取得する。
クエリは単一SELECT、末尾セミコロン・バックスラッシュなし、順序が安定する `ORDER BY` を付ける。
`SELECT *` や大規模テーブル全量よりも対象ID・カラムを絞る。返却値はJSONとして比較される。
全テーブルのバックアップではなく、試験ごとに指定したクエリのスナップショットである。

## 5. AWS接続・権限

AWSプロファイル `screen-test` を組織の認証方式で準備する。SSO利用時の例:

```bash
aws configure sso --profile screen-test
aws sso login --profile screen-test
```

設定JSONの `aws.accountId` に接続を許可するアカウントIDを記載する。
実行時にSTSで照合し、不一致ならS3・SSMと画面操作を行わない。

| 呼び出し元に必要なアクション | 対象・用途 |
| --- | --- |
| `sts:GetCallerIdentity` | 接続アカウント照合 |
| `s3:ListBucket` | 対象バケット。必要に応じて `s3:prefix` 条件で限定 |
| `ssm:SendCommand` | 指定EC2と `AWS-RunShellScript` ドキュメント |
| `ssm:ListCommandInvocations` | Run Commandの完了確認 |
| `ssm:GetCommandInvocation` | 標準出力の取得 |

SSMは読み取りAPIだけではない。`SendCommand` でEC2上にコマンドを送信する。
このツールは `tail -n <行数> -- <固定ログパス>` のみ生成するが、IAM上の
`AWS-RunShellScript` 権限自体は任意のシェル実行能力を持つ。対象EC2を限定し、
より厳しい運用では固定ログ参照専用のSSMドキュメントを管理者が用意して実装を合わせる。

EC2はLinuxを前提とし、SSM Agentの稼働、SSMに接続できるネットワーク、
インスタンスロール（例: `AmazonSSMManagedInstanceCore`）、対象ログの読み取り権限が必要。
SSH鍵や22番ポートは使用しない。macOSからEC2を直接SSH操作する構成ではない。

## 6. 設定ファイル

票ごとの設定は `plans/<suite-id>/config.example.json` を `config.local.json` にコピーして接続値を埋める。
ECサイトのサンプル: `plans/ecsite-sample/config.example.json`（seed・複数クエリ・appLog の例）。

ルートの `npm test` 用に全機能を使用する場合:

```bash
cp config.example.json config.local.json
```

`REPLACE_WITH_...` を実際のアカウントID、バケット、インスタンスID、期待ログに置き換える。
`baseUrl` と `allowedOrigins` を試験環境に合わせる。テストコードも信頼できるものを使用する。
許可originは起点URLの照合であり、ブラウザの遷移先全体をネットワーク制限する機能ではない。

旧Todoのローカル設定（現状のアプリでは動かない）:

```bash
cp config.todo-local.json config.local.json
```

ローカル設定ではS3・EC2を理由付き `NOT_APPLICABLE` として記録し、アプリログは `appLog` で確認する。
AWS確認済みという意味ではない。AWSの設定欠落・認証失敗は成功扱いしない。

DB設定 `expectedBefore` / `expectedAfter` はクエリ名ごとの期待する行オブジェクトの配列（`{"users": [...]}`）。
`unchanged: true` は全クエリの操作前後の一致、`unchanged: ["users"]` は指定したクエリだけの一致を要求する。
seed を使う場合は `expectedBefore` で投入結果を確認し、画面操作の前提が揃ったことを証跡に残す。少なくとも `unchanged` または
`expectedAfter` が必須。各ケースの `title` はPlaywrightの完全なtest名、`spec` は `specs/` からの相対パス。
1ケースで1テストだけ成功した場合に画面確認をPASSとする。skipや対象ゼロ件も成功にしない。

S3は `expectedKeys` の全キーの存在を確認し、内容・ハッシュ・今回新規作成されたことまでは確認しない。
アプリログ（`appLog`）は、ローカルのログファイルの打鍵直前のサイズを記録し、打鍵後に増えた部分だけを `app.log` に保存して `contains` 全文字列を確認する（最大 `waitMs` ミリ秒、既定3000まで追記を待つ）。
試験前から残っているログには一致しない。ファイルが無い・打鍵中に縮んだ（ローテート・切り詰め）場合は FAIL。
ECサイトは `../../../app/app-run.sh` で起動すると `app/logs/app.log`（`APP_LOG_FILE` で変更可）にサーバーログを追記する。`path` にはこの絶対パスを指定する。

EC2は指定ログ末尾の `contains` 全文字列を確認する。試験開始時刻以降だけの抽出ではない。
試験固有のリクエストIDなどを期待値に含め、過去ログを誤って一致させないこと。
ローテーション済みログ・圧縮ログには未対応。SSM出力上限に達する場合はFAILにし、行数の削減を求める。
非同期処理の完了はspec内でアプリの完了表示等を待ってから確認する。S3・ログの業務的な完了待ちは自動では行わない。

## 7. 実行・成果物

設定検証のみ（外部接続なし）:

```bash
bash with-runtime.sh node src/runner.ts --config config.local.json --validate
bash with-runtime.sh npm run test:unit
```

実試験（画面の操作・DB接続・設定したAWS接続を行う）:

```bash
bash with-runtime.sh npm test
```

```text
runs/<UTC日時>-<ID>/
  index.html                全体結果と証跡リンク
  summary.json              機械可読の全体結果
  run.json                  開始時刻・対象No.
  aws-identity.json          AWS照合結果（AWS利用時）
  No1/
    seed.json               投入したSQLファイルとSHA-256（seed指定時）
    db-before.json / db-after.json   クエリ名ごとの行
    app.log                 打鍵中に追記されたアプリログ（appLog指定時）
    checks.json
    playwright.json
    playwright-report/index.html
    browser/.../step-01.png  各操作のスクリーンショット
    s3.json                 オブジェクト一覧
    ssm-command.json         SSMコマンドID
    ec2.json / ec2.log       ログ取得結果
```

終了コードは0=対象確認成功、1=試験・証跡取得失敗または未実施、2=設定等の起動エラー。
結果は実行ごとに別ディレクトリに保存する。接続エラー時のstderrは秘密情報漏えいを避けるため保存しない。
調査時は管理者が適切な端末で個別に接続確認する。
DB・スクリーンショット・trace・ログには業務情報が含まれ得るため、`runs/` とローカル設定はGit管理対象外。
保存先を削除する処理、DB全体の復元、S3削除はこのツールにはない。DBの変更は設定で指定した seed のみ。

## 8. 試験の追加と再実行

試験項目票のNo.に対応する `test('NoN ...', ...)` を `specs/` に追加する。
`evidence.ts` の `step` を使用し、クリック・入力・選択などの操作ごとにスクリーンショットを残す。
判定は `expect` で明示する。DB・S3・ログの期待値を対応する `cases` に追加する。
Markdownからの自動生成・試験中のLLMによる操作変更は行わない。レビュー済みspecを繰り返し実行する。

試験に必要なデータは seed で試験ごとに用意し、再実行しても同じ状態から始まるようにする。
seed は試験用データ（接頭辞付き）だけを削除→登録する。DB全体のベースライン復元・S3掃除は自動実行しない。
登録・更新試験で画面から作られたデータは、次回の seed の削除対象になるよう試験用の接頭辞・値で登録する。
共有DBで別ユーザーが更新すると `unchanged` が失敗するため、専用環境または対象レコードで確認する。

## 9. 構築確認記録

コード・設定例・手順書と、Node・Playwright・Chromiumを配置済み。
実環境への接続先・認証設定はユーザー側の値が必要。
依存ツールの導入だけでDB/AWS疎通が完了したとは扱わない。
構築時の検証結果は `検証結果.md` に記録する。
