## 入力と作業場所

`$ARGUMENTS` から試験項目票1ファイル、対応表、実行設定を受け取る。cwdは `test/01_単体試験/`。

票だけ渡された場合は `screen-test/plans/*/mapping.md` の元票と照合し、一意に対応する設定を探す。複数候補・未生成・ローカル設定未作成なら不足箇所を報告する。別票やルートのサンプル設定で代用しない。試験票は作成時と同じファイルを使う。

## 1. 実施対象の照合

[準備・実施手順](../../../screen-test/試験準備・実施手順.md)、[作成規約](../../../screen-test/テストコード作成規約.md)、元票、mapping.md、spec、設定例と実行設定を読む。

- 票のNo.・シナリオ・操作・期待結果と、対応表・test・casesが1対1で一致することを確認する。件数・順序・対象範囲も確認する。
- 元票の生ファイルのSHA-256を対応表と照合する。異なる場合は差分を確認し、作成スキルによる同期後に実施する。ハッシュだけ書き換えて続行しない。
- spec・実行設定・seed SQLのSQL・assertion・ログ／AWS期待値が対応表と一致することを確認する。seed が試験用データ以外を削除・変更しないことをSQLで確認する。設定例からの接続値補完以外に変更があれば、その根拠を確認する。
- 保留・未確定値・未レビューの変更があれば該当No.と理由を報告して実行しない。設定検証が通るだけで未確定事項を解決済みとしない。
- `_02_異常系` の障害注入は実施しない。対象外と報告する。
- 部分実施はユーザーが対象No.を指定した場合のみ。部分実施用のレビュー済み設定がなければ作成スキルへ戻す。実施スキルがその場でcasesを間引かない。

元票ハッシュの確認例（パスを実際の元票に置き換える）:

```bash
shasum -a 256 '元票のパス'
```

## 2. 実施準備を確認する

[構築手順書](../../../screen-test/構築手順書.md) と対応表を使い、次を確認する。既存の許可・回答は引き継ぎ、同じ確認を繰り返さない。

- ツールが利用可能で、アプリ・DB・認証・初期データが準備されている。
- 対象URL・DB・AWSアカウント・S3・EC2・ログパスが依頼された試験環境である。seed を使う設定（`allowSeed: true`）が共有環境・本番相当を指していない。
- seed によるデータ投入、画面からの更新・削除と、DB読み取り・AWSアクセス・SSMコマンド送信が実行許可の範囲内である。
- appLog を使う場合、アプリが `app/app-run.sh` 等でそのログファイルへ出力している。
- 前回失敗のデータが残っている場合、再実行条件が満たされている。

依存導入・アプリ起動・疎通確認は本スキルで自動実施しない。ユーザーが準備やドキュメントだけを求めている場合は、準備状態と残件を報告し、以下の実試験に進まない。

## 3. 接続せずに検証する

ユーザーのコマンド実行ルールに従って、`screen-test/` で実行する。山括弧は実際のsuite-idに置き換える。

```bash
bash with-runtime.sh node src/runner.ts --config plans/<suite-id>/config.local.json --validate
bash with-runtime.sh npm run typecheck
bash with-runtime.sh node node_modules/@playwright/test/cli.js test 'specs/<suite-id>\.spec\.ts$' --list --reporter=json
```

全体の列挙が対象No.と一致することを確認する。さらに各caseについてrunnerと同じspec・title末尾条件で `--list --reporter=json` を実行し、正しいtestがちょうど1件だけ選択されることを確認する。titleの正規表現記号はリテラルとしてエスケープする。ゼロ件・複数件・別タイトルを実行に進めない。
列挙JSONのskippedは未実行の表示。ここでは合否を判定せず、実試験後のskip・NOT_RUNとは区別する。

`--list` でもspecはimportされる。承認されていないトップレベル通信・コマンド呼び出しがないことをコードで先に確認する。

## 4. レビュー済みの設定で実施する

```bash
bash with-runtime.sh node src/runner.ts --config plans/<suite-id>/config.local.json
```

このコマンドは実際に seed によるDB更新・画面操作・DB接続・設定されたAWS接続を行う。ルートの `npm test` は別の `config.local.json` を読むため、plansの実施には使用しない。

runnerはNo.ごとに事前データ投入→DB事前確認→ログ位置記録→画面操作・撮影→DB事後確認→アプリログ→S3→EC2の順で実行する。seed失敗時は画面操作を実施しない。画面失敗時も事後確認を試みる。通常の失敗はrunnerに集約させ、実施中にコードや期待値を変更しない。

終了コードと出力されたrun-idを記録する。0は設定された確認の成功、1は試験・証跡取得失敗または未実施、2は起動時の設定等のエラー。コードだけでなく結果ファイルの内容も確認する。タイムアウトや中断時に自動再実行しない。

## 5. 結果を集約する

今回の `runs/<run-id>/summary.json` と各No.の `checks.json`、Playwright結果を読む。古いrunの結果を今回の結果として報告しない。

- No.ごとに事前データ・画面・DB・アプリログ・S3・EC2を分けて報告する。checks行数を試験件数にしない。
- いずれかがFAILならそのNo.は不合格。未実施項目が残るNo.は合格にしない。画面NOT_RUNは未実施として併記する。
- NOT_APPLICABLEは根拠のある対象外であり、そのサービスを確認した意味ではない。対象外を成功件数に含めない。
- 結果ファイル欠落・証跡取得失敗・設定エラーは実施失敗または未実施として理由を記載する。画面のみの成功で全体をOKにしない。
- seed.json・PNG・DB前後JSON・app.log・S3一覧・EC2ログ・HTML結果票の保存先を示す。業務データや秘密値をそのままチャットへ転記しない。
- 試験不一致、環境・接続の問題、準備不足を区別して報告し、再実行に必要な事項を示す。

## 完了報告

対象票・対象No.・run-id、No.単位の合格／不合格／未実施件数、対象外サービス、失敗理由と証跡リンクを報告する。未実施なら実施済みと表現しない。試験票・テストコード・期待値は変更しない。

## スコープ外

- 試験項目票の作成・レビュー、テストコードの新規作成・修正
- 依存導入、疎通確認、アプリ起動、AWSインフラ作成
- 設定の seed 以外のデータ準備・DB復元・S3削除・障害注入・再試行
