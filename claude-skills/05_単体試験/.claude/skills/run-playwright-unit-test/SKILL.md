引数で渡された試験項目票ファイル1つ（`$ARGUMENTS`）を読み込み、以下の手順で単体テストを実行してください。パスは `05_単体試験/` を基準に解決する（相対パスなら `試験項目票/試験項目票_{画面名称}_{分類}.md` のように書く）。

## 入力の検証

以下をすべて満たさない場合は、実行せず理由を報告して終了する（部分的な実行はしない）。

- `$ARGUMENTS` がファイルパス1つだけであること（複数パスが渡された場合は「1ファイルのみ対応。分類ごとに個別に呼び直してください」と報告する）
- 指定パスにファイルが実在すること
- ファイル名が `試験項目票_{画面名称}_{分類}.md` の形式であること（`{分類}` が `01_正常系` / `02_異常系` / `03_フロントバリデーション` / `04_サーババリデーション` のいずれかと解釈できること）

## 対象外（実行しない）

ファイル名が `_02_異常系.md` で終わる票は対象外とする。DB接続断・ファイル操作エラー等の外部リソース異常を Playwright で安全に再現できないため。渡された場合は実行せず、「`_02_異常系` は対象外」と理由を報告して終了する（他の3分類 `_01_正常系` / `_03_フロントバリデーション` / `_04_サーババリデーション` は対象）。

## 事前確認

1. 対象アプリ（既定 `http://localhost:8080`）が起動していることを確認する。起動していなければ、起動を促して終了する（起動は本skillの担当外）
2. DB検証が必要な項目がある場合は、Postgres MCP（読み取り専用ユーザーで接続。`../04_製造/docker/setup-readonly-user.sh` で作成）が接続済みであることを確認する。未接続なら、DB検証を行う項目のみ「DB確認未実施（Postgres MCP未接続）」として画面確認のみで判定する

## ファイル名から画面名称・分類を特定する

`試験項目票_{画面名称}_{分類}.md` の形式から `{画面名称}` と `{分類}`（`01_正常系` / `03_フロントバリデーション` / `04_サーババリデーション`）を取り出す。取り出せない場合は要確認事項としてユーザーに確認する。

## 出力先フォルダ構成

結果一式は `試験結果/` 配下に、対象画面名・分類のサブフォルダを作って格納する。

```
試験結果/
  試験結果票_{画面名称}_{分類}_{yyyyMMddHHmm}.html
  {画面名称}/
    {分類}/
      No{No.}_実施キャプチャ_手順{操作手順番号}_{OK/NG}.jpeg
      No{No.}_テーブル確認結果_{OK/NG}.md
      DB確認結果_サマリ.md
```

- `{No.}` は試験項目票のNo.列の値をゼロ埋めせずに使う（例: `No1`, `No2`）
- `{操作手順番号}` は操作手順の何番目のステップかを表す連番（前提条件を満たすための事前操作は含めない）
- `{OK/NG}` はそのNo全体の最終判定（画面・DB双方の結果を踏まえた判定）
- フロントバリデーション（`03_フロントバリデーション`）・サーババリデーション（`04_サーババリデーション`）の項目のうち、操作手順に「開発者ツールでの属性無効化」「curl直叩き」等 Playwright の通常のブラウザ操作・`browser_evaluate` では再現できない回避手順が1つでも含まれる場合は、そのNoは実行せず（キャプチャも撮らず）「未実施（理由）」として記録する（本skillの対象外とする）。一部のステップだけ実行してから未実施にする、という状態は作らない

### `No{No.}_テーブル確認結果_{OK/NG}.md` の内容

以下の構成で記述する（判定結果はファイル名の `{OK/NG}` に表すため、本文には記載しない）。

```markdown
# テーブル確認結果: {画面名称} {分類} No.{No.}

## 確認内容
{期待結果欄のうちDB検証に関する記述}

**確認用クエリ**
​```sql
{DB確認用クエリの該当No.のSQL文}
​```

## 確認結果

{execute_sqlの結果を表形式で記載}
```

### `DB確認結果_サマリ.md` の内容

DB確認用クエリの対象になっているNoのみを対象に、以下の3列表で一覧化する。

| No. | 確認結果 | NG時の補足 |
|-----|---------|-----------|
| {No.} | OK または NG | NGの場合のみ、期待結果とクエリ結果の差分を簡潔に記載。OKの場合は空欄 |

## 手順

1. 試験項目票の表から No./シナリオ/正常異常/前提条件/操作手順/期待結果 と、表の下のDB確認用クエリ（対応No.／確認用クエリ）をパースする
2. `mkdir -p` で `試験結果/{画面名称}/{分類}/` フォルダを作成する（**Playwright MCP は `browser_take_screenshot` の `filename` に指定したパスの親ディレクトリを自動作成しない**ため、撮影前に必ず作成しておく）
3. Noごとに以下を行う:
   0. 操作手順に「開発者ツールでの属性無効化」「curl直叩き」等、Playwright の通常のブラウザ操作・`browser_evaluate` で再現できない回避手順が含まれる場合は、このNoは実行せず（前提条件の準備・撮影も行わず）「未実施（理由）」として記録し、次のNoへ進む
   1. 前提条件を満たす状態にする（画面操作で行う。DBへ直接書き込まない）
   2. 操作手順を1ステップずつ実行する。各ステップで:
      - playwright MCPで該当操作を行う（要素特定は `browser_snapshot` を基本とする）
      - `browser_take_screenshot` で撮影する。`filename` パラメータは **`.mcp.json` の `--output-dir` を経由せず、Claude Codeのセッション自体のcwd（`05_単体試験/`）を基準に解決される**ため、`試験結果/` から始まる相対パス `試験結果/{画面名称}/{分類}/No{No.}_実施キャプチャ_手順{操作手順番号}_PENDING.jpeg` を指定する（`--output-dir` はこの用途では使われない。`filename` を省略した場合のデフォルト名にのみ影響する）
   3. 全ステップ完了後、期待結果と実際の画面状態を比較する
   4. DB確認用クエリに当該Noの行があり、Postgres MCPが接続済みの場合は、そのSQL文を `execute_sql` で実行し、結果を取得する（DB確認用クエリに無いSQL文を推測して実行しない）
   5. 画面・DB双方の結果が期待結果と一致すればOK、一致しなければNGと判定する（DB未接続で確認できない場合は画面結果のみで判定し、その旨を記録する）
   6. 保存した各スクリーンショットの `_PENDING` を最終判定の `_OK`/`_NG` にリネームする（3-0で「未実施」としたNoはキャプチャ自体が存在しないため対象外）
   7. DB確認用クエリを実行した場合は結果を
      `試験結果/{画面名称}/{分類}/No{No.}_テーブル確認結果_{OK/NG}.md`
      に保存する
4. DB確認用クエリを実行したNoが1件以上ある場合、それらを対象に
   `試験結果/{画面名称}/{分類}/DB確認結果_サマリ.md` を作成する
5. `claude-playwrite-unit-test/templates/試験結果票_{画面名称}_{yyyyMMddHHmm}.html` をテンプレートとして
   `試験結果/試験結果票_{画面名称}_{分類}_{実行日時yyyyMMddHHmm}.html` を新規作成する
6. 各Noの `実施日` と `OK/NG`（未実施の項目は「未実施」とその理由）を試験結果票の該当行に記載する
7. 最後に全体の判定結果（OK/NG/未実施の件数）と保存先ファイル一覧を報告する

## スコープ外

- `_02_異常系` の試験項目票の実行（対象外として扱う）
- アプリ・DBの起動（`../04_製造/app`・`../04_製造/docker` の担当）
- 試験項目票の作成・レビュー（`unit-case-writer` / `unit-case-reviewer` の担当）
- 開発者ツール操作・curl直叩き等、Playwright の通常操作で再現できない回避手順の実施
