引数 `$ARGUMENTS` で渡された「設計書ファイルパス」（および省略可能な「出力先ディレクトリ」）をもとに、サーババリデーションの試験項目票を作成または修正してください。`$ARGUMENTS` に「指摘一覧」と「照合元」が含まれる場合は「指摘反映モード」、それ以外は「通常モード」として動作する。`.claude/skills/` は `claude-skills/` を基準に解決する。

## 共通の前提

- 出力先ディレクトリが省略された場合は、設計書ファイルと同じディレクトリとする
- 担当ファイルは `試験項目票_{画面名称}_02_サーババリデーション.md`。他分類のファイルは読み書きしない
- 設計書ファイルパスが省略されている、または指定パスにファイルが無い場合は、保存せず状態「失敗」と不足内容を返す
- 画面名称は、引数で渡されていればそれを用いる。渡されておらず設計書から一意に特定できない（複数画面が記載されている等）場合は、保存せず状態「失敗」と候補の画面名称を返す
- 本skillは `context: fork` でサブエージェントとして動くため、ユーザーに質問するツールは使えない。確認が必要な事項は、単体実行・集約実行を問わず「要確認事項」として結果に含めて返し、該当箇所の作成・反映は保留する。呼び出し元（人と対話しているセッション）がユーザーに確認し、「確認済み回答」を添えて再度呼び出す。確認済み回答が渡された事項は再確認せずその回答を用いる
- 「集約実行」の明示は finalize 等からの呼び出しを示す。振る舞いの違いは、報告を呼び出し元向けの簡潔な形式にすることだけ

## 通常モード（新規作成）

1. `$ARGUMENTS` から設計書ファイルパスと出力先ディレクトリを読み取る
2. 設計書ファイルを読み込み、対象画面のサーバ側（コントローラ・エンティティ制約等）で行われる入力チェック仕様（必須・文字数・形式・相関項目チェック等）を把握する
   - 設計書に記載がなく判断できない項目は、憶測で補わず要確認事項として返し、その項目は起票しない（確認済み回答があればそれに従って起票する）
3. `.claude/skills/create-unit-case-for-screen/references/試験項目票_{画面名称}.md` をテンプレートとして読み込む
4. サーバ処理内のバリデーションに関する異常系の試験項目を洗い出す
   - 対象: 単項目の境界値チェックのうち「エラーとして拒否される側」（例: 文字数上限超過、必須未入力等）、複数項目にまたがる相関項目チェック（例: 開始日>終了日等）
   - フロント側にも同じ検証が実装されている場合は、サーバ視点の項目としてここに起票してよい（フロント側の担当skillと項目が重複してよい）。フロントのチェックを回避してサーバへ直接不正な値が到達したケースも含める。操作手順には、ブラウザの開発者ツールでフロント側のバリデーション属性（`maxlength`・`required`等）を無効化して送信する、またはcurl等でAPIエンドポイントに直接リクエストを送信する等、回避方法を具体的に記述する。期待結果には、レスポンスのHTTPステータスやエラーメッセージ等、確認すべき内容を具体的に記述する
   - 正常に受理される境界値・フロント処理内のバリデーション・サーバエラーはここでは扱わない（他skillの担当）
5. 各項目について No.・シナリオ・正常/異常・前提条件・操作手順・期待結果を表の1行として記述する
   - 正常/異常列には常に「異常」を記載する
   - 操作手順・期待結果内で複数行になる場合は `<br>` で改行する
   - 操作手順・期待結果で画面項目を指す際は、設計書上のid属性やコンポーネント名などの物理名を記載せず、画面に表示されるラベル・プレースホルダ・ボタン文言等の論理名で具体的に記述する
   - 期待結果には表示されるエラーメッセージ文言・画面の状態を具体的に記述する。DB検証が必要な項目は、検証すべき内容を文章で記述する（SQL文そのものは書かない）
6. No（試験順）は、このファイル内で1から始まる連番（ゼロ埋め不要）とし、実行可能な順序になるよう並べる（ファイルをまたいだ通し番号にはしない）
7. DB検証が必要な項目について、表の下の「DB確認用クエリ」セクションに対応No.と確認用クエリ（SQL文）を記載する
8. 該当する試験項目が1件もない場合も、テンプレートのサンプル行（試験項目表のNo.1行、DB確認用クエリ表の`SELECT ...`行）を削除し、見出し行と区切り行のみを残したファイルを作成し、「該当する試験項目なし」の旨を本文に記載する
9. 出力先ディレクトリに `試験項目票_{画面名称}_02_サーババリデーション.md` として保存する
   - 既に同名ファイルが存在する場合、「上書き可」の明示があれば上書きし、無ければ保存せず状態「未保存」と要確認事項（上書きしてよいか）を返す
10. 結果を報告する: 状態（作成／未保存／失敗）、作成した試験項目の件数（0件の場合はその旨）、保存先ファイルパス、要確認事項（あれば）

## 指摘反映モード

`$ARGUMENTS` に「指摘一覧（種別・対象No.・シナリオ・指摘内容・根拠）」と「照合元（設計書／ソース。ソースの場合は対象画面のソースファイルパス）」が含まれる場合は、新規作成ではなく既存の `試験項目票_{画面名称}_02_サーババリデーション.md` に指摘を反映する。通常モードの手順1〜10は行わず、以下の手順で動作する。

1. `$ARGUMENTS` から設計書ファイルパス・出力先ディレクトリ・指摘一覧・照合元（・確認済み回答）を読み取る
2. 出力先ディレクトリの `試験項目票_{画面名称}_02_サーババリデーション.md` を読み込む
   - 存在しない場合は反映せず、状態「失敗」と理由を報告して終了する
3. 設計書を読み込み、指摘の正誤判断に必要な仕様を把握する。照合元がソースの場合は、渡されたソースファイルと関連ソースも読み込む
4. 指摘一覧のうちサーババリデーションの票を対象とするものを反映する。他分類の票を対象とする指摘が混在していても無視する
   - 対象行は、指摘の対象No.とシナリオの両方が一致する行として特定する。一致する行が無い、または複数該当する場合は反映せず、その指摘を要確認事項として返す
   - 編集に先立ち全指摘の対象行を確定し、同じ行に複数の指摘がある場合はまとめて反映する
   - **抜け（対象No.が「(新規)」）**: 試験項目の行を追加する。DB検証が必要な項目はDB確認用クエリにも行を追加する
   - **抜け（既存No.に対するもの）**: 対象行は残し、不足している要素（DB確認用クエリの行、期待結果に不足する記述等）だけを追加する。試験項目の行を重複して追加しない
   - **誤り**: 対象行・DB確認用クエリを修正する。DB確認用クエリの対応No.が試験項目票に実在しない指摘は、指摘内容に従ってクエリ行を削除するか正しい対応No.に修正する
   - **分類誤り（正常/異常列の値だけが誤っている）**: 列の値のみを修正する
   - **分類誤り（他分類に属する項目が含まれている）**: 行を削除せず、反映せずに「他分類への移動が必要な行」として報告する（移動は人が行うか、他分類のskillが抜けとして追加する）
   - **表記ゆれ**: 該当箇所を修正する
   - 反映後、通常モードの手順5〜7と同じ記述ルール（論理名での記述、`<br>` での改行、No.は1始まりの連番かつ実行可能な順序、SQL文はDB確認用クエリセクションに記載）を満たすよう、必要に応じて行の並び替えとNo.の振り直しを行う
   - 行の追加・削除・並び替えでNo.が変わった場合は、DB確認用クエリの対応No.も追従させる
5. 以下の指摘は自動反映せず、その指摘に限り要確認事項として返す（確認済み回答があればそれに従って反映または見送る）
   - 照合元だけでは正誤を判断できない、複数の解釈が成立しうる指摘
   - 照合元がソースで、反映すると設計書の記載と矛盾する指摘（設計書と実装の乖離の可能性があるため）。確認済み回答で設計書側の誤りと判断されている場合は反映し、設計書の修正が必要な旨を報告に含める
6. 反映した内容で同名ファイルに上書き保存する（反映モードでは上書きの確認は不要）。反映の結果、該当する試験項目が0件になった場合は通常モードの手順8と同じ形式にする。逆に「該当する試験項目なし」の記載がある票に1件以上の行が入った場合は、その記述を削除する
7. 結果を報告する: 状態（反映／失敗）、反映した指摘（種別・対象No.・シナリオ）と件数、見送った指摘とその理由、要確認事項（対象の指摘と確認したい内容）、他分類への移動が必要な行、設計書の修正が必要と判断された指摘、保存先ファイルパス

## スコープ外

- 試験項目票のレビューは行わない（`review-unit-case-server-validation` / `review-unit-case-server-validation-from-source` の担当）
- 他分類（正常系・フロントバリデーション・サーバエラー）の試験項目票は作成・変更しない
- 設計書・ソースコードは変更しない
