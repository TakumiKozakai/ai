name: review-unit-testcase-front-validation
description: 設計書（自由形式のMarkdown）とフロントバリデーションの試験項目票（試験項目票_{画面名称}_01_フロントバリデーション.md）を突き合わせ、フロント処理内の入力チェック観点での抜け・誤り・分類誤りをレビューする。「フロントバリデーションの試験項目票を設計書でレビューして」等の依頼、または review-unit-testcase-for-screen から呼び出されて使用する。
---

引数 `$ARGUMENTS` で渡された「設計書ファイルパス」（および省略可能な「試験項目票ディレクトリ」）をもとに、以下の手順でフロントバリデーションの試験項目票をレビューしてください。

1. `$ARGUMENTS` から設計書ファイルパス・試験項目票ディレクトリ・画面名称（大元skillから渡された場合）を読み取る
   - 設計書ファイルパスが省略されている場合は、独断で進めずユーザーに確認する（大元skillから呼び出された場合は渡された値をそのまま用いる）。相対パスの場合はカレントディレクトリ基準で解釈する
   - 試験項目票ディレクトリが省略された場合は、設計書ファイルと同じディレクトリとする
   - 「集約実行」の明示が無い場合は単体実行として振る舞う
2. 設計書を読み込み、対象画面のフロント側（画面・JS等）で行われる入力チェック仕様（必須・文字数・形式・相関項目チェック等）と、その際に表示されるエラーメッセージ文言・画面の状態を把握する
   - 画面名称が渡されていない場合は設計書から読み取り、試験項目票ディレクトリ内の `試験項目票_{画面名称}_*.md`（分類を問わない）と照合して画面を特定する。一致するファイルが1つも無い、または複数画面分の候補があり一意に特定できない場合はユーザーに確認する（担当ファイルの有無はこの時点では判定せず、3で判定する）
   - 設計書に記載がなく判断できない事項（フロント／サーバどちらで検証するか不明等）は、憶測で補わずユーザーに確認する。解消できない場合は該当観点を「未確認」として記録する
3. `試験項目票_{画面名称}_01_フロントバリデーション.md` を読み込み、各行（No./シナリオ/正常異常/前提条件/操作手順/期待結果）と、表の下のDB確認用クエリ（対応No./確認用クエリ）を把握する
   - ファイルが存在しない場合は、実行状態を「未実施」として大元skillに返す（単体実行の場合はチャットで報告する）。エラーとはしない
   - 「該当する試験項目なし」と記載されたファイルの場合は、設計書側にフロント側の入力チェック仕様が存在するかを確認し、存在すれば「抜け」として指摘する
4. 設計書と突き合わせ、以下の観点で指摘を洗い出す
   - **抜け**: 設計書に記載されたフロント側の入力チェック仕様ごとに、「エラーとして拒否される側」の境界値（文字数上限超過、必須未入力等）や相関項目チェック（開始日>終了日等）に対応する行が1件も無いもの
   - **抜け**: 期待結果欄でDB検証が必要と記述されているのに、DB確認用クエリセクションに対応するNo.の行が無いもの（フロントで弾かれサーバに到達しない想定のため通常はDB検証不要。DB検証を求める記述自体が妥当かも確認する）
   - **誤り**: 期待結果に表示されるエラーメッセージ文言が具体的に記載されていない、または設計書の文言と一致しないもの
   - **誤り**: 操作手順・期待結果に記載された遷移先パス・画面の状態が設計書の記載と一致しないもの
   - **誤り**: 操作手順・期待結果で画面項目を指す記述に、設計書上のid属性やコンポーネント名などの物理名がそのまま使われているもの（表示ラベル・プレースホルダ・ボタン文言等の論理名で記述されているべき）。一覧行など対象が複数存在しうる箇所で、対象を一意に特定できる表現になっていないもの
   - **誤り**: No.がこのファイル内で1から始まる連番（ゼロ埋め不要）になっていない、または重複しているもの。他の分類別ファイルとの同一No.は重複として扱わない
   - **誤り**: 前提条件と操作手順・期待結果の間の矛盾
   - **誤り**: No.1から順に実施した場合に成立しない並び（前の項目の結果に依存する項目が先に来ている等）
   - **誤り**: DB確認用クエリの対応No.が試験項目票に実在しないもの、またはクエリの内容が当該行の期待結果の記述と整合していないもの（設計書のDB定義を参照せずに判定できる観点）
   - **誤り**: DB確認用クエリのテーブル名・カラム名・WHERE条件が設計書のDB定義と整合していないもの。設計書にDB定義が無く照合できない場合は、この観点のみを「未確認」とする
   - **分類誤り**: 正常/異常列が「異常」以外の行、または正常に受理される側の境界値・サーバ処理内のバリデーション（フロントチェックを回避する手順を伴うもの）・サーバエラーなど他分類に属する項目が含まれているもの。ただし、フロント・サーバ双方で同じ検証が実装されている場合にフロント視点の項目として起票されているものは、サーババリデーションの試験項目票と重複していても分類誤りとしない
   - **表記ゆれ**: 同一の画面項目・文言に対する表記の不統一、複数行を `<br>` で改行する規則からの逸脱等
5. 見つかった指摘事項を重大度順（抜け＞誤り＞分類誤り＞表記ゆれ）に整理する。各指摘は以下の項目を持つ
   - 種別（抜け／誤り／分類誤り／表記ゆれ）
   - 対象No.（新規に追加すべき項目の指摘の場合は「(新規)」と明記）
   - 指摘内容
   - 根拠（設計書の該当箇所・記載内容）
   - 指摘・根拠に秘密情報が含まれる場合は値をマスクする
6. 集約実行の場合は、指摘一覧・実行状態（成功）・未確認観点を大元skillに返す。この子skill自体はHTMLファイルを作成しない
7. 単体実行の場合
   - 指摘が1件以上あれば、試験項目票ディレクトリに `試験項目票レビュー結果_{画面名称}_01_フロントバリデーション_設計書_{実行日時yyyyMMddHHmm}.html` を新規作成し、種別｜対象No.｜指摘内容｜根拠の4列表として出力する（既存の試験結果票・試験項目票レビュー結果HTMLと同様のスタイル。指摘内容・根拠はHTMLエスケープする）。未確認観点があればHTML内に明記する。既に同名ファイルが存在する場合は上書きせず、末尾に `_2`, `_3` … を付与した名前で保存する
   - 指摘が0件ならファイルを作成せず、確認した観点と未確認観点をチャットで報告する
   - 最後に分類・実行状態（成功／未実施／失敗）・指摘件数・未確認観点と、HTMLを作成した場合はその保存先パスを報告する。未確認観点が残る場合は「レビュー未完了」と明示する
8. 処理中にエラーが発生し完了できない場合は、実行状態を「失敗」とし、失敗理由（秘密情報はマスクする）とともに大元skillに返す（単体実行の場合はチャットで報告する）
9. 試験項目票ファイル自体は変更しない
