引数 `$ARGUMENTS` で渡された「設計書ファイルパス」「対象画面のソースファイルパス（テンプレート・コントローラ等。複数可）」（および省略可能な「出力先ディレクトリ」）をもとに、以下の手順でフロントバリデーションの試験項目票を完成させてください。本skillは現在のセッションで動く司令塔であり、ユーザーとの対話は本skillだけが行う。

## 使用する skill と呼び出し方

| 役割 | skill | 実行主体 |
| --- | --- | --- |
| 作成（通常モード）／指摘反映（指摘反映モード） | `create-unit-case-front-validation` | サブエージェント `unit-case-creator`（Sonnet） |
| レビュー（設計書ベース） | `review-unit-case-front-validation` | サブエージェント `unit-case-reviewer`（Opus） |
| レビュー（ソースベース） | `review-unit-case-front-validation-from-source` | サブエージェント `unit-case-reviewer`（Opus） |

- 3つの skill はいずれも `context: fork` で定義されているため、**必ず Skill ツールで呼び出す**（SKILL.md を自分で読んで手順を実行してはいけない。それではモデルの切り替えと分離が効かない）
- fork された skill は本セッションの会話を見ない。必要な情報はすべて引数の文字列に含めて渡す
- 呼び出し時は常に「集約実行」を明示する（レビューskillがHTMLを作らず結果を返すための指示）。子skillはサブエージェントのためユーザーに質問できず、確認が必要な事項を「要確認事項」（作成・反映）または「未確認観点」（レビュー）として返す
- 引数に含める項目（該当するものだけ）: 集約実行／設計書ファイルパス／ソースファイルパス／出力先ディレクトリ（試験項目票ディレクトリ）／画面名称／確認済み回答／未解決事項／上書き可／指摘一覧／照合元

## 用語

- **確認済み回答**: 子skillから返された要確認事項・未確認観点についてユーザーから得た回答の蓄積。一度得た回答は以降のすべての呼び出し（サイクルBを含む）で毎回引数に含めて渡す
- **再レビュー待ち**: 前回のレビューで未確認だった観点のうち、ユーザーから回答を得て、まだその回答でレビューしていないもの
- **見送り記録**: 反映モードで見送られた指摘（対象No.・シナリオ・指摘内容の要旨・照合元・見送り理由）。同じ指摘が再度返された場合は反映可能な指摘から除く。同一かどうかは「シナリオと指摘内容の要旨」で判断し、判断がつかない場合はユーザーに同一かを確認する
- **反映可能な指摘**: レビューで返された指摘のうち、見送り記録に無いもの
- **サイクルの終了状態**（各サイクルは必ずいずれか1つで終了する）
  - **収束**: 指摘0件、未確認観点なし、再レビュー待ちなし
  - **収束（未確認残存）**: 指摘0件、再レビュー待ちなしだが、ユーザーに確認しても解消できない未確認観点が残る
  - **見送り残存で終了**: 残っている指摘がすべて見送り済みで、反映可能な指摘が無い（再レビュー待ちなし）
  - **上限打ち切り**: 上限回数（5回）のレビューを終えても反映可能な指摘または再レビュー待ちが残る
  - **ユーザー中止**: 対話中にユーザーが中止を指示した

## 手順

1. `$ARGUMENTS` から設計書ファイルパス・ソースファイルパス（複数可）・出力先ディレクトリを読み取る
   - 設計書ファイルパスまたはソースファイルパスが省略されている場合は、独断で進めず最初にまとめてユーザーに確認する。相対パスはカレントディレクトリ基準で解釈する
   - 出力先ディレクトリが省略された場合は、設計書ファイルと同じディレクトリとする
2. 設計書を読み込み、対象画面名称を特定する。特定できない場合はユーザーに確認する
3. 出力先ディレクトリに `試験項目票_{画面名称}_01_フロントバリデーション.md` があるか確認する
   - 無い場合: 作成skillを通常モード（集約実行）で呼び出す。引数に設計書ファイルパス・出力先ディレクトリ・画面名称を含める（子skillは要確認事項に該当する項目を起票せずに保存し、要確認事項を返す）
     - 要確認事項が返された場合: ユーザーに確認する。回答を得られた事項は確認済み回答に加え、確認済み回答と「上書き可」を添えて同じ呼び出しをやり直す。ユーザーも判断できない事項は「未確認残存」として記録し、やり直さずに4へ進む（やり直すのは作成に使える新しい回答を得た場合だけ）。この未確認残存はサイクルAの各レビューに「未解決事項」として渡す
     - 状態「未保存」（既存ファイルがあり上書き可の明示が無い）が返された場合: 上書きしてよいかユーザーに確認し、可なら「上書き可」を添えてやり直す。不可ならそのファイルを使って4へ進む
     - 状態「失敗」が返された場合: 理由を提示し、再試行するか中止するかをユーザーに確認する（中止は7へ進み、両サイクルを「未実施」とする）
   - 有る場合: 作成はスキップし、4へ進む
4. **サイクルA（設計書レビュー）**: 反復回数 N=1 から開始し、以下を繰り返す（N の上限は5）
   1. レビューskill（設計書ベース）を集約実行で呼び出す。引数に設計書ファイルパス・出力先ディレクトリ・画面名称・確認済み回答（全て）・未解決事項（現在の未確認残存）を含め、指摘一覧・実行状態・未確認観点を受け取る。レビューskillは未解決事項のうち照合元で解消できないものを未確認観点に含めて返す。レビューが完了したら再レビュー待ちを空にする
   2. 実行状態が「未実施」（担当ファイルが無い）または「失敗」の場合: 理由を提示し、再試行するか中止するかをユーザーに確認する。再試行は同じ N のまま 4-1 に戻る（未実施の場合は 3 の作成を行ってから戻る）。中止は「ユーザー中止」としてサイクルAを終了し、7へ進む
   3. 未確認観点がある場合: 確認したい内容をユーザーに確認する。回答を得られた観点は回答を確認済み回答に加え、その観点を再レビュー待ちとする。解消できない観点は「未確認残存」として記録する（未確認残存は毎回この反復のレビューが返した未確認観点で置き換える。作成時の未解決事項もレビューを経由して未確認観点に含まれるため、独立に検出されなくても落ちない）
   4. 受け取った指摘から見送り記録と同一のものを除き、「反映可能な指摘」とする
   5. 終了判定を行う。該当すればサイクルAを終了して5へ進む
      - 反映可能な指摘0件・指摘0件・再レビュー待ちなし: 未確認残存が無ければ「収束」、あれば「収束（未確認残存）」
      - 反映可能な指摘0件・見送り済みまたは保留の指摘のみ残存・再レビュー待ちなし: 「見送り残存で終了」
      - N が上限（5）: 「上限打ち切り」。反映は行わず、この反復のレビュー結果を最終指摘として保持する（最終指摘が反映前の状態を指すよう、上限回では反映しない）
   6. 反映可能な指摘が1件以上あれば、作成skillを指摘反映モード（集約実行）で呼び出す。引数に設計書ファイルパス・出力先ディレクトリ・画面名称・反映可能な指摘一覧（種別・対象No.・シナリオ・指摘内容・根拠）・照合元（設計書）・確認済み回答を含め、反映結果を受け取る（画面名称は要確認事項への回答後の再呼び出しにも必ず含める）
      - 要確認事項が返された場合: ユーザーに確認する。反映判断に使える新しい回答を得た指摘だけを、回答を確認済み回答に加えたうえで再度反映モードに渡す。ユーザーが「反映しない」と判断した指摘は見送り記録に加える。ユーザーも判断できない指摘は「保留」として理由を記録し、再呼び出しせずに次の反復へ進む（次のレビューで再び返された場合も、新しい回答が無ければ保留のまま扱い、反映可能な指摘に数えない）。保留は最終報告に載せる
      - 「他分類への移動が必要な行」は見送り記録に加え、最終報告に載せる（本skillは他分類の票を扱わない）
      - 状態「失敗」が返された場合: 理由を記録して次の反復へ進む（次のレビューが同じ指摘を再検出する）。失敗が2回連続した場合は、理由を提示して再試行するか中止するかをユーザーに確認する
   7. N回目の反復結果（指摘件数・反映件数・見送った指摘の概要・実行状態・未確認観点・再レビュー待ち）をチャットに報告し、N を1増やして 4-1 に戻る
   - 対話中にユーザーが中止を明示的に指示した場合は「ユーザー中止」としてサイクルAを終了し、7へ進む（サイクルBは「未実施」とする）
5. サイクルAの終了状態に応じて分岐する
   - 「収束」「収束（未確認残存）」「見送り残存で終了」: 6へ進む
   - 「上限打ち切り」: サイクルBへ進むかここで終了するかをユーザーに確認する。終了する場合はサイクルBを「未実施」として7へ進む
6. **サイクルB（ソースレビュー）**: 反復回数 N=1 から開始し、サイクルAの 4-1〜4-7 と同じ構造で繰り返す（N の上限は5）。サイクルAとの違いは以下のみ
   - 4-1 の代わりにレビューskill（ソースベース）を集約実行で呼び出す。引数にソースファイルパス・出力先ディレクトリ・画面名称・確認済み回答（サイクルAで得たものを含む全て）・未解決事項（現在の未確認残存。サイクルB開始時の初期値はサイクルA終了時点の未確認残存で、以降は 4-3 の置き換えに従う）を含める
   - 4-6 の照合元は「ソース（ソースファイルパスを含む）」とする。設計書の記載と矛盾する指摘は反映モード側で要確認事項として返るので、ユーザーに確認する。ユーザーが設計書側の誤りと判断して反映した指摘は、設計書の修正が必要な旨を最終報告に含める（本skillは設計書を修正しない）
   - 見送り記録と保留はサイクルAから引き継ぐ。ただし見送り理由・保留理由が「設計書だけでは判断できない」「設計書にDB定義が無い」等、照合元に依存するものは見送り記録・保留から外し、ソース（DBスキーマを含む）を根拠に反映可能な指摘として扱う。ユーザーが明示的に「反映しない」と判断した指摘は見送りを維持する
   - 再レビュー待ちはサイクルBの開始時点で空にする。未確認残存はサイクルA終了時点の内容を初期値として引き継ぐ（サイクルA終了時点の再レビュー待ち・未確認残存は最終報告用に別途保持する）。確認済み回答は引き継ぐ
   - 終了先: 「ユーザー中止」を含むいずれの終了状態でも7へ進む（5には戻らない）。サイクルAの終了状態は更新しない
7. サイクルAまたはBのいずれかが「上限打ち切り」で終了している場合のみ（もう一方が中止・未実施でも）、出力先ディレクトリに `試験項目票レビュー結果_{画面名称}_01_フロントバリデーション_finalize_{実行日時yyyyMMddHHmm}.html` を新規作成する（既存の試験結果票・試験項目票レビュー結果HTMLと同様のスタイル）。構成は以下
   - 見出し・対象画面・設計書パス・ソースパス・実行日時
   - サイクル別の反復回数と終了状態の表
   - 最終指摘の表（サイクル｜種別｜対象No.｜指摘内容｜根拠）。各サイクルの指摘は、そのサイクルの打ち切り時点の試験項目票に対するものであることを明記する
   - 各サイクル終了時点の未確認残存の観点、再レビュー待ち（回答は得たがその回答でのレビューが未実施の観点。観点・回答・未検証である旨）、見送った指摘・保留した指摘（対象No.・シナリオ・理由）、他分類への移動が必要な行
   - 指摘0件で上限打ち切りになった場合は、打ち切り理由（再レビュー待ちが残るため）を明記する
   - 指摘内容・根拠に含まれる設計書・コードの引用はHTMLエスケープし、秘密情報はマスクする
   - 既に同名ファイルが存在する場合は上書きせず、末尾に `_2`, `_3` … を付与した名前で保存する
   - 上限打ち切りが無い場合はHTMLを作成しない
8. 最後に以下を報告する
   - サイクルA・Bそれぞれの反復回数と終了状態（実施しなかったサイクルは「未実施」）、上限打ち切りの場合は最終指摘件数
   - 見送った指摘（理由付き）とその件数、保留した指摘（理由付き）、他分類への移動が必要な行
   - 各サイクル終了時点の未確認残存の観点と再レビュー待ち（回答・未検証である旨）、反映に失敗して残った指摘
   - 設計書の修正が必要と判断された指摘
   - 試験項目票の保存先パス、HTMLを作成した場合はそのパス
   - 終了状態にかかわらず、自動反映のみで完結させず最終的な人間による目視レビューを推奨する旨

## スコープ外

- 他分類（正常系・サーババリデーション・サーバエラー）の試験項目票は扱わない（それぞれの finalize skill の担当）
- 試験の実施は行わない（`run-playwright-unit-test` の担当）
- 設計書・ソースコードは変更しない（乖離が見つかった場合は報告のみ）
- 反映の部分失敗からの再開は保証しない（次の反復のレビューが再検出する前提。上限5回と最終的な目視レビューで担保する）
