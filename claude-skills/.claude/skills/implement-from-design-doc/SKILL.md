# implement-from-design-doc

設計書（Markdownファイルパス）を入力として受け取り、その内容をもとにコードを実装する。

## 入力の受け取り方

- 引数 `$ARGUMENTS` で設計書ファイルパスを受け取る。パスが相対パスの場合はカレントディレクトリ基準で解釈する。
- 引数が省略されている場合、または指定されたパスにファイルが存在しない場合は、独断で進めず設計書パスをユーザーに確認する。
- 実装先プロジェクト（ルートディレクトリ）は設計書の保存場所と必ずしも一致しないため、着手前にユーザーに確認する。設計書自体に実装先が明記されている場合は、それをユーザーに提示し確認を取ってから進める。実装先確定後も、設計書自体の参照先は最初に確認したパスのまま変えない。

## 実装先プロジェクトの調査

- 実装に着手する前に、実装先プロジェクトの `CLAUDE.md` / `AGENTS.md`（あれば）、依存定義・ロックファイル（package.json、pom.xml等）、既存コード、CI設定を確認し、技術スタック・ディレクトリ構成・命名規則・テスト/lintコマンドを把握する。
- 技術スタックや構成を設計書の記載のみで決め打ちしない。設計書の記載と実際のプロジェクト構成が矛盾する場合は、どちらを採用するかユーザーに確認する。

## 作業前の状態確認

- 実装に着手する前に `git status` 等で作業ツリーの状態を確認し、今回のタスクと無関係な既存の変更・未追跡ファイルがある場合は、それらを巻き込まないよう変更範囲を明確に区別する。
- 今回実装で変更する予定のファイル自体に既存の未コミット変更がある場合は、その内容を上書き・破棄せず、両立できないときはどう扱うかをユーザーに確認してから進める。

## 設計情報の解釈

- 設計書に書かれた内容のみを実装対象とし、記載のない仕様を憶測で補わない。
- 設計書に未記載・曖昧・矛盾・TODO/TBD等がある箇所は、実装に着手する前にすべて洗い出し、必要な回答をユーザーから得る。

## 実装方針の提示と承認

- 調査・確認が終わった時点で、実装方針（新規作成・変更するファイル一覧と概要）をユーザーに提示し、承認を得てから実装に着手する。
- 設計書が存在すること自体を実装の承認とはみなさない。必ず別途明示的な承認を得る。
- 実装中に、提示した方針からの逸脱が必要になった場合は、その場でユーザーに再確認する。

## 実装時の注意

- 破壊的な操作（force push、DBマイグレーション、rm -rf、既存データの削除等）を行う前は必ずユーザーに確認を取る。
- APIキー・トークン等の秘密情報を出力・コミットしない。

## テスト・lint

- 実装内容に応じてテストを追加・更新する。
- 実装先プロジェクトのテスト・lintコマンドを実行する。
- 今回の変更に起因するテスト・lintの失敗は修正し、再実行して解消を確認する。
- テストを書かない・実行しない場合、コマンドが存在しない・依存関係や権限・環境の問題で実行できない場合、実行して失敗し修正しても解消しない場合など、理由を問わず実行不能・未実施・失敗のいずれかに該当する限り、その旨と理由を報告し「完了」とは報告しない。

## スコープ外

- 設計書自体の作成・更新は行わない。設計書の記載と既存コードが矛盾する場合も、矛盾解消のために設計書側を書き換えることはせず、ユーザーへの確認によって解決する。

## 出力後の報告

- 実装した（新規作成・変更した）ファイルの一覧を報告する。
- 実行したテスト・lintコマンドとその結果を報告する。
- 対応できなかった事項（未実装の仕様、確認が取れず保留にした箇所等）があれば一覧で報告する。
