引数 `$ARGUMENTS` で渡された「対象画面のソースファイルパス（複数可）」と「試験項目票ディレクトリ」をもとに、以下の手順でサーババリデーションの試験項目票をレビューしてください。

1. `$ARGUMENTS` からソースファイルパス・試験項目票ディレクトリ・画面名称（大元skillから渡された場合）を読み取る
   - ソースファイルパスまたは試験項目票ディレクトリが省略されている場合は、独断で進めず実行状態「失敗」と不足している引数を返す。相対パスの場合はカレントディレクトリ基準で解釈する
   - 「集約実行」の明示が無い場合は単体実行として振る舞う（違いはHTMLを作成するかどうかだけ）
   - 本skillは `context: fork` でサブエージェントとして動くため、ユーザーに質問するツールは使えない。単体実行・集約実行を問わずユーザーに確認せず、確認したい内容は未確認観点に添えて返す（呼び出し元がユーザーに確認し、「確認済み回答」を添えて再度呼び出す）。確認済み回答が渡された事項は再確認せずその回答を用いる。確認済み回答が照合元の記載と矛盾する場合は確認済み回答を優先し、その旨を指摘の根拠に明記する
   - 「未解決事項」（呼び出し元が作成時に判断できなかった事項）が渡された場合は、照合元で解消できるか確認し、解消できないものは確認したい内容を添えて未確認観点に含めて返す
2. ソースファイルと関連ソース（コントローラ・フォームクラスのバリデーションアノテーション・Validatorクラス・コントローラ内の独自チェック・メッセージ定義・エラー時に再表示するテンプレート等）を読み込み、サーバ側で行われる入力チェック（必須・文字数・形式・相関項目チェック等）と、その際のレスポンス（HTTPステータス・エラーメッセージ文言・再表示される画面の状態）を把握する
   - 画面名称が渡されていない場合はソース（テンプレート名・画面タイトル等）から読み取り、試験項目票ディレクトリ内の `試験項目票_{画面名称}_*.md`（分類を問わない）と照合して画面を特定する。一致するファイルが1つも無い、または複数画面分の候補があり一意に特定できない場合は、実行状態を「失敗」とし確認したい内容（候補ファイル）を添えて返す（担当ファイルの有無はこの時点では判定せず、3で判定する）
   - 参照すべき関連ソース（バリデーション定義・メッセージ定義等）が特定できない場合は、憶測で補わず、確認したい内容を添えて該当観点を「未確認」として記録する
3. `試験項目票_{画面名称}_02_サーババリデーション.md` を読み込み、各行（No./シナリオ/正常異常/前提条件/操作手順/期待結果）と、表の下のDB確認用クエリ（対応No./確認用クエリ）を把握する
   - ファイルが存在しない場合は、実行状態を「未実施」として大元skillに返す（単体実行の場合はチャットで報告する）。エラーとはしない
   - 「該当する試験項目なし」と記載されたファイルの場合は、ソース側にサーバ側の入力チェックが存在するかを確認し、存在すれば「抜け」として指摘する
4. ソースコードと突き合わせ、以下の観点で指摘を洗い出す
   - **抜け**: ソース上のサーバ側入力チェックごとに、「エラーとして拒否される側」の境界値（文字数上限超過、必須未入力、形式不正等）や相関項目チェックに対応する行が1件も無いもの
   - **抜け**: フロント側にも同じ検証がある項目について、フロントのチェックを回避してサーバへ直接不正な値が到達するケースが無いもの
   - **抜け**: 期待結果欄でDB検証が必要と記述されているのに、DB確認用クエリセクションに対応するNo.の行が無いもの（拒否された入力がDBに反映されていないことの確認等）
   - **誤り**: フロントのチェックを回避する項目で、操作手順に回避方法（ブラウザの開発者ツールでフロント側のバリデーション属性を無効化して送信する、curl等でエンドポイントに直接リクエストを送信する等）が具体的に記載されていないもの。また、その回避方法が実装上成立しないもの（存在しないエンドポイント・パラメータ名等）
   - **誤り**: 期待結果にレスポンスのHTTPステータス・エラーメッセージ文言・画面の状態が具体的に記載されていない、またはコントローラの処理（`BindingResult` の扱い、リダイレクト先、例外ハンドラ）・メッセージ定義と一致しないもの
   - **誤り**: 操作手順・期待結果に記載された遷移先パス・エンドポイントがコントローラのマッピングと一致しないもの
   - **誤り**: 操作手順・期待結果で画面項目を指す記述に、`id` 属性やclass名などのソースコード上の物理名がそのまま使われているもの（表示ラベル・プレースホルダ・ボタン文言等の論理名で記述されているべき。ただし、フロントチェック回避のために開発者ツールやcurlで操作する対象の属性名・パラメータ名は、回避手順として必要な範囲で記載してよい）。一覧行など対象が複数存在しうる箇所で、対象を一意に特定できる表現になっていないもの
   - **誤り**: No.がこのファイル内で1から始まる連番（ゼロ埋め不要）になっていない、または重複しているもの。他の分類別ファイルとの同一No.は重複として扱わない
   - **誤り**: 前提条件と操作手順・期待結果の間の矛盾
   - **誤り**: No.1から順に実施した場合に成立しない並び（前の項目の結果に依存する項目が先に来ている等）
   - **誤り**: DB確認用クエリの対応No.が試験項目票に実在しないもの、またはクエリの内容が当該行の期待結果の記述と整合していないもの（DBスキーマを参照せずに判定できる観点）
   - **誤り**: DB確認用クエリのテーブル名・カラム名・WHERE条件が対象のDBスキーマと整合していないもの。DBスキーマはpostgres MCPの `list_objects`／`get_object_details` 等で確認する。MCPが利用できない等でスキーマを参照できない場合は、この観点のみを「未確認」とする
   - **誤り**: 期待結果にSQL文そのものが記載されているもの（DB検証が必要な内容は文章で記述し、SQL文はDB確認用クエリセクションに記載する規則）
   - **分類誤り**: 正常/異常列が「異常」以外の行、または正常に受理される側の境界値・サーバエラー（DBエラー等の外部リソース起因）など他分類に属する項目が含まれているもの。ただし、フロント・サーバ双方で同じ検証が実装されている場合にサーバ視点の項目として起票されているものは、フロントバリデーションの試験項目票と重複していても分類誤りとしない
   - **表記ゆれ**: 同一の画面項目・文言に対する表記の不統一、複数行を `<br>` で改行する規則からの逸脱等
   - 画面のサーバ処理を検証するための直接リクエストは画面試験の一部として扱い、API用試験項目票の対象として除外しない
5. 見つかった指摘事項を重大度順（抜け＞誤り＞分類誤り＞表記ゆれ）に整理する。各指摘は以下の項目を持つ
   - 種別（抜け／誤り／分類誤り／表記ゆれ）
   - 対象No.（新規に追加すべき項目の指摘の場合は「(新規)」と明記）
   - 指摘内容
   - 根拠となるソースコードの箇所（ファイルパス・行、アノテーション・メッセージ文言等）。確認済み回答だけを根拠とする指摘は、その回答の該当内容を根拠とする
   - 指摘・根拠に秘密情報が含まれる場合は値をマスクする
6. 集約実行の場合は、指摘一覧（種別・対象No.・シナリオ・指摘内容・根拠）・実行状態（成功）・未確認観点（確認したい内容を添える）を大元skillに返す。この子skill自体はHTMLファイルを作成しない
7. 単体実行の場合
   - 指摘が1件以上あれば、試験項目票ディレクトリに `試験項目票レビュー結果_{画面名称}_02_サーババリデーション_ソース_{実行日時yyyyMMddHHmm}.html` を新規作成し、種別｜対象No.｜指摘内容｜根拠の4列表として出力する（既存の試験結果票・試験項目票レビュー結果HTMLと同様のスタイル。指摘内容・根拠に含まれるコード等はHTMLエスケープする）。未確認観点があればHTML内に明記する。既に同名ファイルが存在する場合は上書きせず、末尾に `_2`, `_3` … を付与した名前で保存する
   - 指摘が0件ならファイルを作成せず、確認した観点と未確認観点をチャットで報告する
   - 最後に分類・実行状態（成功／未実施／失敗）・指摘件数・未確認観点と、HTMLを作成した場合はその保存先パスを報告する。未確認観点が残る場合は「レビュー未完了」と明示する
8. 処理中にエラーが発生し完了できない場合は、実行状態を「失敗」とし、失敗理由（秘密情報はマスクする）とともに大元skillに返す（単体実行の場合はチャットで報告する）
9. 試験項目票ファイル・ソースコードは変更しない
