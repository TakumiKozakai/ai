# implement-from-design-doc-diff

設計書（Markdownファイルパス）と比較基準となるコミットIDを入力として受け取り、指定コミットIDから
HEADまでの設計書の変更差分のみをコードに実装する。

## 入力の受け取り方

- 引数 `$ARGUMENTS` で設計書ファイルパスと比較基準となるコミットIDを受け取る。パスが相対パスの場合はカレントディレクトリ基準で解釈する。
- 設計書ファイルパス・コミットIDのいずれかが省略されている場合は、独断で進めずユーザーに確認する。コミットIDを自動で提案することはしない。
- 実装先プロジェクト（ルートディレクトリ）は設計書の保存場所と必ずしも一致しないため、着手前にユーザーに確認する。設計書自体に実装先が明記されている場合は、それをユーザーに提示し確認を取ってから進める。実装先確定後も、設計書自体の参照先は最初に確認したパスのまま変えない。

## 差分の検知

- 設計書が属するリポジトリのHEAD（直近のコミット。未コミットの変更は比較対象に含めない）時点の設計書ファイルの内容と、指定コミットID時点の内容を `git diff` で比較し、変更差分を取得する。
- 指定コミットIDの時点に設計書ファイルが存在しない場合、コミットIDが不正で解決できない場合、HEAD時点で設計書ファイルが存在しない・リネームされている場合は、独断で進めずユーザーに確認する。
- 設計書ファイルが指定コミットIDからHEADまでの間で変更されていない場合（差分なし）は、実装すべき変更がない旨を報告し、実装には着手しない。

## 差分の解釈

- 実装対象は差分に限定する。差分の解釈にあたっては設計書全体（HEAD時点の内容）を文脈として参照してよいが、未コミットの変更は文脈参照にも含めない。
- 実装対象は差分が示す仕様変更と、それに伴い必要となる関連コード・テストの変更に限定する。
- 差分の追加・削除行を機械的に機能の追加・削除と解釈しない。記述の移動・整理等で仕様自体は変わっていない可能性がある場合、仕様変更かどうかをユーザーに確認する。
- 差分に記載のない仕様を憶測で補わない。差分内容に未記載・曖昧・矛盾・TODO/TBD等がある箇所は、実装に着手する前にすべて洗い出し、必要な回答をユーザーから得る。

## 実装先プロジェクトの調査

- 実装に着手する前に、実装先プロジェクトの `CLAUDE.md` / `AGENTS.md`（あれば）、依存定義・ロックファイル（package.json、pom.xml等）、既存コード、CI設定を確認し、技術スタック・ディレクトリ構成・命名規則・テスト/lintコマンドを把握する。
- 技術スタックや構成を設計書の記載のみで決め打ちしない。設計書の記載と実際のプロジェクト構成が矛盾する場合は、どちらを採用するかユーザーに確認する。

## 作業前の状態確認

- 実装に着手する前に `git status` 等で作業ツリーの状態を確認し、今回のタスクと無関係な既存の変更・未追跡ファイルがある場合は、それらを巻き込まないよう変更範囲を明確に区別する。
- 今回実装で変更する予定のファイル自体に既存の未コミット変更がある場合は、その内容を上書き・破棄せず、両立できないときはどう扱うかをユーザーに確認してから進める。

## 実装方針の提示と承認

- 調査・確認が終わった時点で、実装方針（差分に基づく新規作成・変更するファイル一覧と概要）をユーザーに提示し、承認を得てから実装に着手する。
- 設計書または差分が存在すること自体を実装の承認とはみなさない。必ず別途明示的な承認を得る。
- 実装中に、提示した方針からの逸脱が必要になった場合は、その場でユーザーに再確認する。

## 実装時の注意

- 破壊的な操作（force push、DBマイグレーション、rm -rf、既存データの削除等）を行う前は必ずユーザーに確認を取る。
- APIキー・トークン等の秘密情報を出力・コミットしない。

## テスト・lint

- 実装内容に応じてテストを追加・更新する。
- 実装先プロジェクトのテスト・lintコマンドを実行する。
- 今回の変更に起因するテスト・lintの失敗は修正し、再実行して解消を確認する。
- テストを書かない・実行しない場合、コマンドが存在しない・依存関係や権限・環境の問題で実行できない場合、実行して失敗し修正しても解消しない場合など、理由を問わず実行不能・未実施・失敗のいずれかに該当する限り、その旨と理由を報告し「完了」とは報告しない。

## スコープ外

- 設計書自体の作成・更新は行わない。設計書の記載と既存コードが矛盾する場合も、矛盾解消のために設計書側を書き換えることはせず、ユーザーへの確認によって解決する。
- コミットIDの自動提案は行わない。省略・不正な場合は必ずユーザーに確認する。
- 設計書全体を対象とする実装は行わない（既存の `implement-from-design-doc` の担当）。既存の `implement-from-design-doc` 自体の変更・統合は行わない。

## 出力後の報告

- 差分が無かった場合はその旨のみ報告し、以降の項目は不要。
- 実装した（新規作成・変更した）ファイルの一覧を報告する。
- 実行したテスト・lintコマンドとその結果を報告する。
- 対応できなかった事項（未実装の仕様、確認が取れず保留にした箇所等）があれば一覧で報告する。
