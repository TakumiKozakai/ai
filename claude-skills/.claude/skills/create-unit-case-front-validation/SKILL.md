引数 `$ARGUMENTS` で渡された「設計書ファイルパス」（および省略可能な「出力先ディレクトリ」）をもとに、以下の手順でフロントバリデーションの試験項目票を作成してください。

1. `$ARGUMENTS` から設計書ファイルパスと出力先ディレクトリを読み取る
   - 出力先ディレクトリが省略された場合は、設計書ファイルと同じディレクトリを出力先とする
   - 「指摘一覧」と「照合元」が渡されている場合は、下記「指摘反映モード」の手順で動作する
2. 設計書ファイルを読み込み、対象画面のフロント側（画面・JS等）で行われる入力チェック仕様（必須・文字数・形式・相関項目チェック等）を把握する
   - 設計書に記載がなく判断できない項目は、憶測で補わずユーザーに確認する
3. `.claude/skills/create-unit-case-for-screen/references/試験項目票_{画面名称}.md`（`claude-skills/` を基準に解決する）をテンプレートとして読み込む
4. フロント処理内のバリデーションに関する異常系の試験項目を洗い出す
   - 対象: 単項目の境界値チェックのうち「エラーとして拒否される側」（例: 文字数上限超過、必須未入力等）、複数項目にまたがる相関項目チェック（例: 開始日>終了日等）
   - サーバ側にも同じ検証が実装されている場合は、フロント視点の項目としてここに起票してよい（サーバ側の担当skillと項目が重複してよい）
   - 正常に受理される境界値・サーバ処理内のバリデーション・サーバエラーはここでは扱わない（他skillの担当）
5. 各項目について No.・シナリオ・正常/異常・前提条件・操作手順・期待結果を表の1行として記述する
   - 正常/異常列には常に「異常」を記載する
   - 操作手順・期待結果内で複数行になる場合は `<br>` で改行する
   - 操作手順・期待結果で画面項目を指す際は、設計書上のid属性やコンポーネント名などの物理名を記載せず、画面に表示されるラベル・プレースホルダ・ボタン文言等の論理名で具体的に記述する
     - 遷移先パス（URL）は画面項目そのものではないため、そのまま記載してよい
   - 期待結果には表示されるエラーメッセージ文言を具体的に記述する
6. No（試験順）は、このファイル内で1から始まる連番（ゼロ埋め不要）とし、実行可能な順序になるよう並べる（ファイルをまたいだ通し番号にはしない）
7. DB検証が必要な項目（フロントで弾かれサーバに到達しない想定のため通常は不要）がある場合、表の下の「DB確認用クエリ」セクションに対応No.と確認用クエリ（SQL文）を記載する
8. 該当する試験項目が1件もない場合も、テンプレートのサンプル行（試験項目表のNo.1行、DB確認用クエリ表の`SELECT ...`行）を削除し、見出し行と区切り行のみを残したファイルを作成し、「該当する試験項目なし」の旨を本文に記載する
9. 出力先ディレクトリに `試験項目票_{画面名称}_01_フロントバリデーション.md` として保存する
   - 既に同名ファイルが存在する場合は上書きしてよいか確認する
10. 作成した試験項目の件数（0件の場合はその旨）と保存先ファイルパスを報告する

## 指摘反映モード

`$ARGUMENTS`（または大元skill）から「指摘一覧（指摘ID・種別・対象No.・指摘内容・根拠・対象行の原文。ファイル間移動の指摘は移動元分類・移動先分類・元No.・行本文・対応するDB確認用クエリを含む）」と「照合元（設計書／ソース。ソースの場合は対象画面のソースファイルパス）」が渡された場合は、新規作成ではなく既存の `試験項目票_{画面名称}_01_フロントバリデーション.md` に指摘を反映する。通常モードの手順1〜10は行わず、以下の手順で動作する。

1. `$ARGUMENTS` から設計書ファイルパス・出力先ディレクトリ（省略時は設計書ファイルと同じディレクトリ）・指摘一覧・照合元を読み取る
   - 指摘IDと対象行の原文は通常 create-unit-case-for-screen が付与して渡す。直接呼び出されて付与されていない場合は、本skillが手順2の読み込み後に付与する（指摘IDは連番、対象行の原文は対象No.の試験項目行またはDB確認用クエリ行から読み取る）
2. 出力先ディレクトリの `試験項目票_{画面名称}_01_フロントバリデーション.md` を読み込む
   - 存在しない場合は、通常モードの手順で新規作成し、その旨を報告して終了する（指摘の反映は行わない）
3. 設計書を読み込み、指摘の正誤判断に必要な仕様を把握する。照合元がソースの場合は、渡されたソースファイルと関連ソースも読み込む
4. 指摘一覧のうち本分類（フロントバリデーション）を対象とするものだけを反映する。他分類向けの指摘が混在していても無視する
   - 本ファイルの既存行を修正・削除する指摘（誤り・既存No.の抜け・列値の訂正・表記ゆれ・移動元の削除）は、指摘に付与された「対象行の原文」と内容が一致する行を対象として特定する。試験項目行は行本文（シナリオ・前提条件・操作手順・期待結果）、DB確認用クエリ行は対応No.と確認用クエリで照合する。対象No.は補助情報とし、原文と一致しない場合は原文を優先する。一致する行が見つからない、または複数該当する場合は反映せずユーザーに確認する。移動先への追加にはこの特定は適用せず、後述のとおり一致行が無いことを確認して追加する
   - 編集に先立ち、本ファイルの既存行を対象とする全指摘について対象行を原文で確定してから編集する。同じ行に複数の指摘がある場合はまとめて1回で反映する（先に反映した修正で後の指摘の原文照合が失敗しないようにする）
   - DB確認用クエリ行を対象とする指摘のうち「対応No.が試験項目票に実在しない」ものは、指摘内容に従ってクエリ行を削除するか正しい対応No.に修正する。どちらにすべきか判断できない場合はユーザーに確認する。テーブル名・カラム名・WHERE条件等のSQL本文の誤りは「誤り」としてクエリ内容を修正する
   - **抜け（対象No.が「(新規)」）**: 試験項目の行を追加する。DB検証が必要な項目はDB確認用クエリにも行を追加する
   - **抜け（既存No.に対するもの）**: 対象No.の行はそのまま残し、不足している要素（DB確認用クエリの行、期待結果に不足する記述等）だけを追加する。試験項目の行を重複して追加しない
   - **誤り**: 該当No.の行・DB確認用クエリを修正する
   - **分類誤り（列値の訂正）**: 正常/異常列の値のみを修正し、行の移動・削除は行わない
   - **分類誤り（ファイル間移動・本分類が移動先）**: 渡された行本文（移動対象の行に対する他の訂正指摘は大元skillが統合済み）と対応するDB確認用クエリをもとに、本分類の記述ルールに合わせて行（必要ならクエリ行も）を追加する。同じ項目を指す「抜け（(新規)）」の指摘がある場合は重複して追加しない。行本文が一致する行が既に存在する場合（前回の反映で追加済み）は行を重複追加しない。ただし、移動データに対応するDB確認用クエリがあるのにクエリ行が無い・内容や対応No.が一致しない場合は、その不足分を補ってから追加成功として扱う（行本文の一致だけでは追加成功とみなさない）
   - **分類誤り（ファイル間移動・本分類が移動元）**: 渡された行本文（シナリオ・前提条件・操作手順・期待結果）と内容が一致する行を特定し、その行と対応するDB確認用クエリの行を削除する。No.は1巡目の並び替えで変わっている可能性があるため、行の特定にNo.を使わない。一致する行が見つからない、または複数該当する場合は削除せずユーザーに確認する（大元skillは移動先への追加が保存成功した指摘だけを削除側として渡してくる）
   - **表記ゆれ**: 該当箇所を修正する
   - 反映後、通常モードの手順5〜7と同じ記述ルール（論理名での記述、`<br>` での改行、No.は1始まりの連番かつ実行可能な順序、SQL文はDB確認用クエリセクションに記載）を満たすよう、必要に応じて行の並び替えとNo.の振り直しを行う
   - 行の追加・削除・並び替えでNo.が変わった場合は、DB確認用クエリの対応No.も追従させる
5. 以下の指摘は自動反映せず、その指摘に限りユーザーに確認してから反映または見送る
   - 照合元だけでは正誤を判断できない、複数の解釈が成立しうる指摘
   - 照合元がソースで、反映すると設計書の記載と矛盾する指摘（設計書と実装の乖離の可能性があるため）。ユーザーが設計書側の誤りと判断した場合は反映し、設計書の修正が必要な旨を報告に含める
6. 反映した内容で同名ファイルに上書き保存する（反映モードでは上書きの確認は不要）。反映の結果、該当する試験項目が0件になった場合は通常モードの手順8と同じ形式にする。逆に、0件（「該当する試験項目なし」の記載あり）の票に追加・移動で1件以上の行が入った場合は、「該当する試験項目なし」の記述を削除する
7. 指摘IDごとの状態（反映済み／見送り（理由付き）／未反映（失敗理由付き）。対象No.は入力時点のものを併記）、設計書の修正が必要と判断された指摘、保存先ファイルパスを報告する。ファイル間移動で本分類が移動先の場合は、追加の保存に成功した移動指摘を明示し、実際に保存した行本文と対応するDB確認用クエリ（本分類の記述ルールに合わせて整形した後の内容）を返す（大元skillが移動元の削除可否と、再試行時の追加済み判定に使うため）。保存に失敗した場合は、この呼び出しで渡された指摘をすべて未反映として報告する
