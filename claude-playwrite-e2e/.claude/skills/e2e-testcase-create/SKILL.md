name: e2e-testcase-create
description: 対象画面のソースコード（テンプレート・コントローラ等）を読み込み、試験項目票(e2e/試験項目票_{画面名称}.md)を作成する。「〜画面の試験項目票を作って」「テストケースを作成して」等の依頼で使用する。
---

引数で渡された画面のソースファイルパス（$ARGUMENTS）をもとに、以下の手順で試験項目票を作成してください。

1. 対象画面のテンプレート・関連するコントローラのソースコードを読み込み、画面の要素（id属性等）・入力項目・バリデーション仕様・遷移先を把握する
2. `../claude-skills/.claude/skills/create-unit-testcase-for-screen/references/試験項目票_{画面名称}.md` をテンプレートとして読み込む
   - テンプレートが存在しない場合はその旨を報告し、作成を中断する
3. 正常系・異常系（バリデーションエラー等）・境界値（一覧0件等）を網羅するよう試験項目を洗い出す
4. 各項目について No.・シナリオ・正常/異常・前提条件・操作手順・期待結果を表の1行として記述する
   - 操作手順・期待結果内で複数行になる場合は `<br>` で改行する
   - 操作手順・期待結果で画面項目（入力欄・ボタン・リンク・チェックボックス・エラーメッセージ等）を指す際は、`id`属性やclass名などのソースコード上の物理名を記載せず、画面に表示されるラベル・プレースホルダ・ボタン文言等の論理名で具体的に記述する
     - 例: `todo-title-input` → 「タイトル入力欄」、`todo-add-button` → 「追加ボタン」、`class="error"` の要素 → 「エラーメッセージ」
     - 一覧行など同一の論理名を持つ要素が複数存在しうる場合は「対象の◯◯」等、対象を一意に特定できる表現を用いる
     - 遷移先パス（URL）は画面項目そのものではないため、そのまま記載してよい
   - 正常/異常列には「正常」または「異常」のいずれかを記載する
   - DB検証が必要な項目は、期待結果欄に検証すべき内容を文章で記述する（SQL文そのものは書かない）
5. No（試験順）は、画面内で1から始まる連番（ゼロ埋め不要）とし、かつNo.1から順に実施することを前提に、実行可能な順序になるよう並べる
   - DBへの永続化を伴わない項目（表示確認・バリデーションエラー等）を先に配置する
   - 新規データを登録する項目は、その登録結果を前提条件とする項目より前に配置する
   - 複数件存在を前提とする境界値項目は、必要件数を満たした直後に配置し、無駄な追加登録が発生しないようにする
   - 削除・全件クリアなど後続の前提条件を崩す破壊的な項目は最後にまとめて配置する。特に一覧0件確認は最終項目とする
   - 上記だけでは解決できず他Noと独立したデータが必要な項目は、当該No自身の前提条件に「なければ事前に登録」等、自己完結する記述を残す
6. DB検証が必要な項目について、表の下の「DB確認用クエリ」セクションに対応No.と確認用クエリ（SQL文）を記載する
7. `e2e/試験項目票_{画面名称}.md` として保存する
   - 既に同名ファイルが存在する場合は上書きしてよいか確認する
8. 作成した試験項目の件数と保存先ファイルパスを報告する
